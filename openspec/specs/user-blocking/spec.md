# user-blocking Specification

## Purpose

定义用户主动屏蔽、双向社交隔离和关系清理边界，使被屏蔽关系不能继续通过好友、空闲列表或普通房间邀请产生定向互动。

## Requirements

### Requirement: 用户可以定向屏蔽其他用户
系统 MUST 允许已认证用户屏蔽另一名用户，不允许屏蔽自己。屏蔽事实只向发起者本人可见；重复屏蔽 MUST 返回同一有效结果，不向目标用户发送屏蔽者身份或原因通知。

#### Scenario: 创建屏蔽
- **WHEN** 用户屏蔽另一名存在的用户
- **THEN** 系统保存从调用者指向目标用户的唯一屏蔽事实并返回最小结果

#### Scenario: 屏蔽自己
- **WHEN** 用户将自己作为屏蔽目标
- **THEN** 系统拒绝操作且不创建记录

### Requirement: 任一方向屏蔽隔离社交互动
系统 MUST 在好友请求、好友列表、空闲用户列表和普通房间邀请中执行双向隔离：只要任一方屏蔽另一方，双方都不能看到彼此的社交条目、建立好友关系或发送普通房间邀请。服务端 MUST 在写入事务中重新检查屏蔽事实，不能只依赖列表过滤。

#### Scenario: 被屏蔽用户直接发起请求
- **WHEN** 被屏蔽用户绕过客户端直接向屏蔽者发送好友请求或普通房间邀请
- **THEN** 系统返回一致的目标不可用结果且不暴露屏蔽方向

#### Scenario: 屏蔽双方查询空闲列表
- **WHEN** 任一方查询好友或可邀请用户列表
- **THEN** 双方均看不到对方的社交条目和空闲状态

### Requirement: 屏蔽原子清理现有社交关系
系统 MUST 在创建屏蔽的同一持久化事务中解除双方好友关系，终结双方待处理好友请求，并取消双方之间仍待处理的普通房间邀请。已接受或已消费的历史记录可保留最小审计事实，但不能继续授予权限。

#### Scenario: 屏蔽现有好友
- **WHEN** 用户屏蔽当前好友
- **THEN** 屏蔽、好友解除、待处理请求和待处理邀请清理全部成功或全部失败

### Requirement: 解除屏蔽不恢复历史关系
系统 MUST 允许屏蔽发起者解除自己的有效屏蔽。解除后系统不得自动恢复旧好友关系、请求或邀请；双方如需重新成为好友或发送邀请，MUST 重新完成对应流程。

#### Scenario: 解除屏蔽
- **WHEN** 屏蔽发起者解除有效屏蔽
- **THEN** 屏蔽失效且历史好友关系和邀请保持失效

### Requirement: 屏蔽操作可安全重试
系统 MUST 要求创建和解除屏蔽携带调用者生成的 UUID 请求标识，并保证相同命令重试返回原结果、不同命令复用标识返回稳定冲突。

#### Scenario: 并发重复屏蔽
- **WHEN** 同一用户并发使用相同请求标识屏蔽同一目标
- **THEN** 系统只保存一条有效屏蔽和一组关系清理结果
