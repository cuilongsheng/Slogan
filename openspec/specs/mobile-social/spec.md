# mobile-social Specification

## Purpose

Allows mobile phone users to manage friends, available users, friend requests, blocks and received room invitations through the personal authorization interface, retain server-side relationship ruling, paging and idempotent command boundaries, and use the existing room entry process to process invitations.

## Requirements

### Requirement: My social list and commands

The mobile terminal MUST display friends, available users, two-way friend requests and personal blocking through the server page authorized by me, and provide applicable initiation, acceptance, rejection, withdrawal, deletion and release operations. All write commands MUST use the UUID idempotent identification generated by the caller, and retrying with the same uncertain result MUST reuse the original identification. The page MUST not display precise online times, room activity details, or blocked direction inference.

#### Scenario: Uncertain response to friend request acceptance

- **WHEN** The user retries the same action after encountering network failure when accepting the request.
- **THEN** Request to use the same idempotent ID, do not declare both parties to be friends before success

### Requirement: Invitation to my room follows the existing joining steps.

The mobile terminal MUST display the pending room invitations sent to me in pagination. Users can choose to view the corresponding room details and continue with the original preparation for joining, or refuse the invitation with the idempotent identifier; the page MUST not consume invitations on its own or bypass passwords, capacity, rules and account qualifications.

#### Scenario: Open the received invitation

- **WHEN** User selects a room in a pending invitation
- **THEN** The path to enter the existing room details will be re-verified by the server when actually joining.
