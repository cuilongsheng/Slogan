## Context

See `proposal.md`'s motivation. The current API is NestJS modular monolith, PostgreSQL saves persistent facts, and Redis only undertakes temporary coordination; `openapi/openapi.yaml` is generated by NestJS code-first and is the only API contract. An existing standalone room-speech worker is already capable of hiding participant subscriptions via LiveKit to enable the room's audio track, calling replaceable STT by short window, and clearing the audio and full transcription after processing, but the orchestration is currently owned by the `speech-safety` module and only rooms for `sensitiveSpeechDetectionEnabled=true` are discovered.

Post-meeting keywords cannot be recovered from security risk events because the risk events do not contain the original text and have different purposes. It requires extracting anonymous candidates while the full transcript is still in single process memory, while ensuring that failure of either safety classification or learning candidate does not destroy the other, nor does the full transcript enter PostgreSQL, Redis, queues, or logs. Final room summaries and wordbooks actively saved by users are allowed persistent facts.

## Goals / Non-Goals

**Goals:**

- Improve media subscription, STT, consent generation verification and content cleaning to a neutral room voice processing arrangement, so that security identification and post-meeting keywords share a short window transliteration but keep the fact of their respective fields isolated.
- Support for post-recoverable and idempotent summary generation using bounded, unmembered, unordered temporary aggregations.
- Protect summary and wordbook APIs with server-side participation qualifications and userId ownership, and provide stable concurrent results for creation, editing, collection, and deletion.
- Keep old clients, old rooms, and security-only rooms compatible; all new capabilities are turned off by default.

**Non-Goals:**

- Does not introduce a second persistent audio subscriber, a second STT call, or a new external AI generation provider.
- Do not hold room summaries responsible for private notes, line-by-word subtitles, full summaries, dictionaries, or security evidence.
- Does not pre-build the view model for the front end, nor changes the existing UI or mobile process.

## Decisions

### 1. Add independent switch and independent consent purpose

Room adds `postRoomKeywordsEnabled Boolean @default(false)`, both instant and reservation creation DTOs can be submitted clearly, and the list, details, sharing analysis and reservation details are returned uniformly. The database trigger and domain policy both prevent modification after creation. Creating an enabled room requires `POST_ROOM_KEYWORDS_ENABLED=true` and the shared room-speech worker readiness is valid; rooms with turned off capabilities are not affected by dependency status.

`SpeechProcessingPurpose` adds `POST_ROOM_KEYWORDS`, supporting independent notice version. Join, reserve/confirm, token renewal and worker processing separately calculate the purpose set required for the room: the security switch requires `ROOM_SAFETY_DETECTION`, the keyword switch requires `POST_ROOM_KEYWORDS`, and both must be satisfied at the same time when they are turned on. Each destination retains a separate consent generation; any required generation changes before and after STT drop the window and release the content. Undoing invalidation of the issuance associated with the enabled room via existing transaction mode, writing the reliable `REVOKE_IDENTITY` command and disconnecting the member, does not generate a security fact.

Selecting independent switches and destinations, rather than multiplexing safety switches, is to meet destination restrictions and user instruction accuracy. Choosing to be immutable when created instead of dynamically switching in the session is to allow all members to see stable processing conditions before joining.

### 2. Neutral arrangement only fans out complete transcription in memory

Added `room-speech-processing` application boundary, taking over room discovery, participant purpose context, an STT session, generation secondary verification and final string clearing. The existing worker and media source continue to run as separate processes; it acquires the same fencing lease as the OPEN room with any room voice purpose enabled.

A successful transcription is fanned out through the in-process synchronous consumer interface:

1. `speech-safety` consumer implements versioned risk rules and only saves the existing minimum risk/degradation facts;
2. `post-room-learning` consumer extracts anonymous candidates, submitting only roomId, candidate type, normalized text, count, and extractor version.

The consumer cannot hold the original audio, nor can it return the complete transcription to the asynchronous queue. The orchestration calls the consumer using an independent copy or a read-only value, and overwrites the reference immediately after all consumers complete or fail; the failure of a single consumer only records the degradation of its own capabilities and does not cancel another allowed purpose. This avoids two hidden participants and double STT costs, and also prevents `speech-safety` from owning the learning content.

The alternative is to create another keyword worker and subscribe/translate separately. This solution has intuitive boundaries, but it will repeatedly send member audio, increase costs, and withdraw race conditions, so it is not adopted.

### 3. Deterministic candidate extraction precedes external generation model

V1 uses a versioned local candidate extraction policy: unify Unicode/case and punctuation, filter stop words, obvious contact information and unsafe lengths, extract one to three-word keywords and commonly used short expressions of controlled length, and set an upper limit on the number of candidates for each window and room. Finally sorted stably by frequency, room theme relevance, type and standardized text, and intercepted bounded results.

Candidate extraction does not receive userId, membershipId or participant identity. The current demand only requires lightweight keywords and common expressions. The deterministic solution can be tested offline, there is no new content supplier, and it reduces the need for complete transcription to be sent out again. If you want to introduce model interpretation or summary in the future, you need independent change, provider data policy and new acceptance evidence.

### 4. Redis only saves anonymous candidate working sets with TTL

Each room uses a temporary candidate set protected by the current fencing token. The key value only contains the normalized candidate, type, aggregate count and extractor version, and does not include the speaker, window time, sentence-by-sentence order or complete transcription. The number of characters, the number of tokens, and the total entry limit are respectively set for single keywords and short expressions; TTL covers the expected room end time and limited retry window after the end.

The old fencing token cannot be added to, read from the snapshot required for finalization, or delete the new holder's working set. When Redis is unavailable, it stops new keyword candidate processing and writes a destination-level downgrade status without content. Human voice and security consumers continue to run. Temporary keys will be deleted when finalization is successful, confirmed to be unavailable, timed out, or maintained for maintenance.

Redis was chosen instead of PostgreSQL to save candidates because candidates are still temporary content in processing and should not become long-term persistent facts. Choosing anonymous counting instead of saving window text preserves limited progress across worker restarts while reducing the likelihood of recovering a full conversation.

### 5. PostgreSQL saves rollup status, final entries, and resumable tasks

New model:

- `RoomKeywordSummary`: At most one line per room, save `COLLECTING | PENDING | READY | UNAVAILABLE`, topic snapshot, extractor version, generation/failure time, normalized failure category and version; rooms with turned off capabilities are not built, and the API derives `DISABLED`.
- `RoomKeywordSummaryItem`: Save `KEYWORD | EXPRESSION`, display text, normalized text, and stable rank; unique constraint prevents duplicate normalized entries from same summary, does not save speaker or timeline.
- `RoomKeywordSummaryJob`: A persistent task for each room, including `PENDING | RUNNING | COMPLETED | FAILED`, attempt, nextAttemptAt, leaseId/lockedUntil and deadline, supporting `FOR UPDATE SKIP LOCKED` collection and expired lease recovery.

Create `COLLECTING` summary line when room creation is enabled. The same database transaction that entered room `ENDING/ENDED` pushed it to `PENDING` and upsert the job; repeated end events only hit the same row. After receiving the job, the runner reads the anonymous candidate snapshot with valid lease and room fencing boundaries, writes the final items, updates `READY` and completes the job in one transaction. Update `UNAVAILABLE` when there are not enough candidates, the candidates have expired, or the retry deadline has been reached. Press compare-and-delete to clean up Redis after submission; cleanup retry must not overwrite the READY content.

### 6. Participate in fact-protected shared summary reading

`GET /v1/rooms/{roomId}/keyword-summary` derives userId from current identity, requires room to be `ENDING/ENDED` and actual RoomMembership exists for this user. `LEFT`, `REMOVED`, or room host changes do not erase participation that has occurred; RoomReservation and RoomInvitation are not eligible. Returns a unified envelope: `DISABLED | PENDING | READY | UNAVAILABLE`, only READY carries items sorted by rank. Unrelevant access returns a stable rejection that does not reveal the existence of the resource.

This qualification reuses the "actual membership" semantics of room-history, but reads it through the public application port, without deep importing the rooms repository.

### 7. The vocabulary book is a user's private copy and uses the explicit version

Added `VocabularyItem`: userId, kind, displayText, normalizedText, note, favorite, version, sourceSummaryItemId, createdAt, updatedAt. `sourceSummaryItemId` is only used for authorization and source idempotent, and does not expose room member information in the list; the only `(userId, sourceSummaryItemId)` prevents repeated imports from the same source.

Added `VocabularyCommand` to save userId, clientRequestId, action, payloadHash, resultItemId and time; `POST /v1/me/vocabulary-items` checks summary access, write commands and entries within the transaction, the same UUID/payload returns the original result, and changes the payload conflict. GET uses the `(updatedAt,id)` keyset cursor, and writes favorite/kind into the cursor and then verifies it to prevent cross-filter reuse.

`PUT /v1/me/vocabulary-items/{itemId}` accepts `expectedVersion`, display text, empty personal notes and favorite, updated using userId + id + version conditions. `DELETE /v1/me/vocabulary-items/{itemId}` accepts `expectedVersion` and physically deletes the private entry; after deletion, the old command cannot be restored because the record does not exist. All endpoints only use the current identity and do not accept target userIds.

Choosing to copy as a user-private entry instead of letting the wordbook reference and directly display the shared item is to allow users to edit/delete without rewriting the room summary, and to decouple the future summary retention strategy from personal learning materials.

### 8. API and stability errors

Continue to use NestJS code-first Swagger to generate `openapi/openapi.yaml` and do not maintain the second contract. Main interface:

- `PUT /v1/me/speech-processing-consents/post-room-keywords`
- `GET /v1/rooms/{roomId}/keyword-summary`
- `POST /v1/me/vocabulary-items`
- `GET /v1/me/vocabulary-items`
- `PUT /v1/me/vocabulary-items/{itemId}`
- `DELETE /v1/me/vocabulary-items/{itemId}`

Room creation, list, details, sharing and reservation responses increased by `postRoomKeywordsEnabled`. Stable business error covers at least `POST_ROOM_KEYWORDS_UNAVAILABLE`, `POST_ROOM_KEYWORDS_CONSENT_REQUIRED`, `VOCABULARY_VERSION_CONFLICT`, `IDEMPOTENCY_KEY_REUSED` and general validation/authorization results. Summarized normal PENDING/UNAVAILABLE uses the status in the success response and does not disguise expected results as HTTP failures.

### 9. Observability and retention boundaries

Logs and spans only record roomId, stage, purpose, provider category, window bytes, candidate count, job status, elapsed time, and normalization errors, but do not record audio, transcript, candidate text, final item text, note, or complete provider response. Candidate content must also not enter exception messages, fixture snapshots, or queue payloads.

The final summary and the words actively saved by the user belong to V1. Persistent facts are allowed, and the temporary STT is not applicable. The maximum seven-day period is not applicable; the specific long-term retention is determined by subsequent data governance changes. If the user deletes this word entry, the private copy will be removed immediately and the shared summary will not be deleted. The maintenance task cleans up expired temporary keys, final job technical records, and orphan command records, but does not delete the READY summary before the retention policy is approved.

## Risks / Trade-offs

- [Risk] Deterministic n-gram extraction quality is lower than dedicated language model → Guaranteed interpretable baseline with versioned fixtures, stopwords, length/PII filtering and minimum quality threshold; insufficient quality returns UNAVAILABLE, no made-up content.
- [Risk] Redis failure or TTL expiration prevents summary generation → runner uses bounded retries, eventually explicitly UNAVAILABLE; room end and live voice do not wait to be generated.
- [Risk] Same translation fanout increases the life cycle of content in memory → consumers must be synchronized, have timeouts, and cannot queue complete text; orchestration clears references and tests success/failure/shutdown paths immediately after all consumers converge.
- [Risk] The combination of consent generation for two processing purposes creates a race condition → STT reads the same purpose set before and after and compares it item by item; any change in the required purpose discards the window and triggers access convergence.
- [Risk] The final summary may contain contact information or private fragments → window extraction and finalization perform two filterings, strictly limit the token/character length, and do not save the original text of the failure; the real smoke still requires manual inspection of the output.
- [Trade-off] Selecting the same word from different rooms will form different private entries → V1 only idempotent from the same source to avoid conflicts with the unique constraints of the global text after editing; cross-source merging is left for subsequent word book enhancements.
- [Trade-off] The keyword room depends on the voice worker of Cloud smoke which is currently unfinished → local implementation and fake/runtime verification can be completed, but the real Cloud/provider task must remain unfinished and must not be archived according to the latest user requirements.

## Migration Plan

1. Added `POST_ROOM_KEYWORDS`, summary/task/wordbook enums and tables, and Room default false columns and immutable triggers; proved old rows remain false with migration test including historical Rooms.
2. Deploy API and worker code compatible with old requests, keeping `POST_ROOM_KEYWORDS_ENABLED=false`; first generate and verify OpenAPI, run empty library upgrade and existing migration chain.
3. Start worker and verify PostgreSQL, Redis, LiveKit/STT readiness, fencing, temporary cleanup, and old security identification regression; only then allow creation of new keyword-enabled rooms.
4. Use real LiveKit Cloud and qualified STT provider to complete double room smoke and record the environment and results before deciding to enable production; when there are no credentials, the task remains BLOCKED and the change remains active.

The rollback is performed in the order of first closing the new one, then stopping the processing, and finally rolling back the application: close `POST_ROOM_KEYWORDS_ENABLED`, reject the new enabled room, wait or converge the ended job to UNAVAILABLE, stop the new consumer, and then roll back the application. New columns/tables and already generated anonymous summaries/user wordbooks are not deleted, so that the old binary can ignore additional schema, and also avoid emergency rollback from damaging the user's actively saved content; Redis temporary keys are cleaned up by TTL and maintenance commands. Physically delete the schema or persistent content only after subsequent independent data migrations are approved.

- Migration: historical Room default value, trigger immutability, empty library complete migration chain, Prisma validate/generate.
- Unit: destination collection and generation, candidate normalization/PII/length/sorting, no member attribution, summary state machine, wordbook policy, cursor and idempotent hash.
- Integration: real PostgreSQL/Redis fencing, temporary candidate TTL, duplicate end, stale lease, READY atomic commit, UNAVAILABLE convergence, delete cleanup and concurrent versions.
- E2E: instant/appointment switch, consent isolation, join/renew/withdraw, participant permissions, summary status, wordbook CRUD/filter/idempotent and override.
- Runtime: independent worker uses fake media/STT to perform dual-purpose single transcoding, failure of one consumer does not affect the other, restart recovery, shutdown content cleaning and memory/Redis/log without complete transcoding.
- Contract/structure: OpenAPI generates diff, format, build, dependency boundaries, complete affected-scope tests, change/main specs strict validation.
- External: Real LiveKit Cloud + dual-session, end-of-build, recall, faildown, and content checks for qualified STT providers; explicitly BLOCKED when not executed, cannot be marked as PASS or archived.
