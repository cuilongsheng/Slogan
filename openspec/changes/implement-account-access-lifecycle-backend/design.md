## Context

See `proposal.md`'s motivation. The current NestJS API already has Google/WeChat OAuth adapter, unique `OAuthIdentity` with `issuer + subject`, short-term access JWT, persistent session and refresh rotation/replay revoke; all authentication paths ultimately use `User.status = ACTIVE` to determine that the session is available. `UserStatus` already contains `DELETED`, but there is no account deletion time, mobile phone number identity, OTP challenge, login method binding or full account account deletion transaction.

PostgreSQL is the persistent truth for accounts, identities, sessions, and business relationships; Redis has been used for ad hoc coordination and throttling. LiveKit undo convergence via persistent `RealtimeCommand` outbox. OpenAPI continues to be generated by NestJS code-first, with `openapi/openapi.yaml` being the only contract. Mobile phone number, verification code and provider credentials are highly sensitive data and cannot be entered into ordinary logs, audit details or test fixtures.

## Goals / Non-Goals

**Goals:**

- Add mobile phone number OTP registration/login and logged-in binding without changing the existing OAuth login contract.
- Use database unique constraints, Redis atomic challenge and current account status to ensure concurrency security, anti-enumeration and one-time consumption.
- Design soft account deletion as a persistent operation that immediately blocks server access, reliably revokes real-time identities, and converges cross-module relationships.
- Let the background investigation read only the minimum necessary status of the deleted account, and leave no sensitive content audit for each visit.

**Non-Goals:**

- Does not design email passwords, mobile phone number changing/unbinding, data migration of two existing accounts or account recovery.
- Don't treat OTP or OAuth as strong real name/age proof.
- Do not determine long-term retention or perform physical deletion in this design.

## Decisions

### 1. The mobile phone number identity only saves the versioned search summary and minimum mask.

Add `PhoneIdentity`, each account has at most one mobile phone number identity, and create unique constraints on `phoneLookupVersion + phoneLookupHash`. The server first uses a reliable international number parsing library to normalize the input to E.164, and then uses independent `PHONE_IDENTITY_PEPPER` to do HMAC; the database does not save the complete E.164. In order for `GET /v1/me/login-methods` to display prompts, only the country calling code and the last two digits of the minimum mask fields that cannot be used for delivery, verification time and userId are saved.

hash version is fixed to participate in unique key and configuration verification; when replacing pepper, dual version migration must be done first, and environment variables cannot be modified directly. The alternative is to save the encrypted mobile phone number in the database, but there is currently no approved requirement to retrieve, change the number, or view the complete number in the background. There is no need to increase the decryption key and leakage surface.

### 2. Redis saves short-term OTP challenges, PostgreSQL only saves the identity facts after consumption

The SMS module uses Redis Lua atomic maintenance challenge through `PhoneChallengeStore` port: random challenge id, mobile phone number digest, verification code HMAC, purpose, expiration time, resend time, remaining attempts and consumption status. The verification code is generated from a cryptographically secure random source and only exists in the synchronization scope of the calling SMS adapter; logs and exceptions only receive contentless provider categories and error enumerations.

Public login, logged-in binding and account deletion re-authentication use different namespaces/purposes, and the challenge cannot be reused across purposes. The verification script checks digest, purpose, expiration, number of attempts, and code digest in one atomic operation; at most one concurrent verification succeeds. Returns a short-term verification grant after success. The grant binds the mobile phone number summary, purpose, current userId (if applicable) and random nonce, and compare-and-delete after the corresponding database transaction is successful. When a transaction fails, only the same request context can be retried within the grant validity period and cannot be consumed for another purpose.

The alternative is PostgreSQL OTP tables. It is easier to do cross-transaction recovery, but it will put high-frequency, short-term verification code status into the long-term fact database and increase the cleaning/backup exposure; this project already has Redis atomic coordination, so it is not used.

### 3. SMS provider is accessed through independent adapter and strict feature gate

Added `SmsProvider` port, which only accepts standardized numbers, one-time verification codes, templates, locale and random associated ids. The environment configuration includes function switches, provider category, base URL, credentials, sender/template, timeout, supported regions, challenge TTL, number of attempts, resend cooling, limits for each dimension, and hash pepper. Lack of Redis, provider security configuration or support region must block readiness when mobile phone number authentication is enabled; existing OAuth API can be started independently when turned off.

provider timeout returns uncertain results and does not automatically switch to the second provider or send repeatedly. The client waits for cooling and re-requests a new challenge, and the old challenge is overwritten or invalidated. The real provider's number coverage, sender compliance, delivery, cost and credential smoke are deployment evidence and are not replaced by the fake adapter.

### 4. Login and binding share the same authentication primitive, but use different application commands.

Added public interface:

- `POST /v1/auth/phone/challenges`: Request login OTP;
- `POST /v1/auth/phone/exchange`: Verify and find/create mobile phone number account, issue session;
- Existing `POST /v1/auth/oauth/{provider}/exchange` remains compatible.

The logged in interface has been added:

- `GET /v1/me/login-methods`: only returns the category, verification time and mobile phone number mask;
- `POST /v1/me/login-methods/phone/challenges` and `/confirm`;
- `POST /v1/me/login-methods/oauth/{provider}/link`。

OAuth link reuses the provider adapter to verify the authorization code, but executes `linkIdentity(currentUserId, identity)` and never calls `findOrCreateUser` for first login. Both mobile phone number and OAuth binding first lock the current user and verify `ACTIVE` in the serializable transaction, and then rely on the global identity unique key and `(userId, provider)`/`userId` unique key to decide CREATED, ALREADY_LINKED or CONFLICT. provider email, nickname and avatar are only used as first-time information suggestions and are never associated keys.

This limits "merging" to multiple authenticated login methods belonging to an existing userId. `AUTH_IDENTITY_ALREADY_BOUND` is returned when two existing platform accounts conflict; the scheme of automatically relocating rooms, cases, wordbooks or audits is irreversible and lacks product rules, so it cannot be implemented.

### 5. All authentication paths re-read the account status before issuing

OTP exchange, OAuth exchange, link, session issue, refresh and access guard all must verify from PostgreSQL that the user is still `ACTIVE`. When the OAuth identity already exists but the account number is `DISABLED/DELETED`, a unified unavailable error is returned, and the "Create after not found" branch cannot be taken. PhoneIdentity continues to occupy the summary for the canceled account, preventing the creation of a replacement account through the original number.

Keep JWT only containing `sub` and session id; role, account status and login method do not write long-lived claims. The existing session active query has been filtered by `ACTIVE`, and the extended test covers all new entries.

### 6. account deletion using short-term step-up proof and persistent idempotent commands

Account account deletion is a security-sensitive action, and the current access token is not sufficient for separate authorization. Added an interface to generate `ACCOUNT_DELETE` proof based on the user's bound method: a dedicated OTP challenge for the mobile phone number; Google/WeChat re-exchanges the authorization code and confirms that the returned identity belongs to the current userId. The proof only contains userId, identity type, purpose, issued/expires and nonce, and is valid for a short period of time.

`POST /v1/me/account/deletion` accepts proof, explicit confirmation and `clientRequestId`. `AccountLifecycleCommand` saves userId, action, request id, payload hash, status and minimum result snapshot, unique to `(userId, clientRequestId)`. Retrying with the same load returns the original result and changes the load conflict. Reject within the transaction when there is a valid administrative role to prevent the only administrator or case handler from disappearing through the ordinary self-service entrance; role handover follows administrative role management.

The alternative is to just require the current JWT or SMS confirmation text, but it doesn't protect against stolen access tokens, so it's not used.

### 7. Core account deletion fact is atomically committed, external undo is converged through outbox

Account lifecycle repository in a PostgreSQL serializable transaction:

1. Lock user and idempotent command, verify `ACTIVE`, proof and no valid administrative role;
2. Set `status = DELETED`, `deletedAt`, cancel all AuthSession;
3. Increment the credentialVersion of all active memberships for this user, make the memberships leave, and write `REVOKE_IDENTITY` for each issued identity;
4. Reuse existing room host leave rules to generate takeover or end facts for the OPEN room it hosts; cancel its future reservations, hosted SCHEDULED rooms and pending invitations;
5. Terminate pending friend requests/invitations and clear persistent qualifications for Redis presence. Public queries continue to be filtered with `User.status = ACTIVE`;
6. Revoke its outstanding realtime issuance and effective administrative role (normal self-service entrance is theoretically zero), and submit the minimum account life cycle audit and command results.

LiveKit deletion of participants, deletion/update of rooms and Redis presence cleanup are retried by existing durable command/maintenance runner. The account deletion response will only be returned after the account status, database qualification expiration and outbox are all submitted; the temporary failure of the external provider will not make the old API token valid again. For Redis cleanup failure, short TTL and `ACTIVE` database checksum combined to prevent rediscovery.

To avoid auth deep import into rooms/social/backoffice repository, add account-lifecycle application boundary and dedicated transaction port; its Prisma adapter has this cross-domain account deletion transaction and reuses the public pure policy/transaction helper. Other modules only expose necessary life cycle rules and do not call each other's internal infrastructure.

### 8. Deletion is access status, not evidence deletion

Soft account deletion preserves stable userId, PhoneIdentity/OAuthIdentity occupancy, security cases, penalties, appeals, audits, room history, anonymized summaries, and user save content. Normal users and public APIs uniformly filter non-ACTIVE accounts; no recovery, identity release or physical deletion paths are added. Subsequent data governance changes determine retention periods, anonymization, and physical cleanup, and migrate these facts when needed.

This option prevents users from circumventing penalties by deleting the account, and also prevents the current change from arbitrarily deleting data that is still under investigation, audit, or user-saved data. The price is that the provider identity and mobile phone number summary remain occupied until the governance policy is approved, which must be specified in the privacy statement.

### 9. Restricted account query reuses real-time RBAC and auditing

Added `ACCOUNT_RESTRICTED_RECORD_READ` permission, only mapped to `PLATFORM_ADMIN` and `SAFETY_OFFICER`. `GET /v1/backoffice/accounts/{userId}/restricted-record` reads the current role each time and returns the account id/status/timestamps, login method category, minimum profile snapshot, and security case/restriction/appeal references in the same controlled query. Non-existent and unauthorized use stable non-disclosure error.

Both success and rejection are written as BackofficeAuditEvent, which only contains actor, roles, target userId, request id, result and normalized reason. Both response schema and audit detail types prohibit full phone number/hash, provider subject/token, verification code, private notes and content data. OPERATIONS_ANALYST and AUDITOR do not automatically gain this read capability due to existing summary/audit permissions.

### 10. OpenAPI, errors and cleanup maintain a single contract

All new DTOs/controllers generated from NestJS Swagger metadata `openapi/openapi.yaml`; implementations must not handwrite a second contract. Stable errors cover at least: mobile phone number format/region, rate limited, challenge invalid/expired/attempt exhausted, provider unavailable/timeout/uncertain, identity bound, account unavailable, step-up invalid, administrative role preventing account deletion, idempotent conflict and restricted record rejection.

Maintenance tasks only clean up expired challenge/grant, expired stream keys, and account command technical records that have reached the retention period; they do not clean up PhoneIdentity/OAuthIdentity occupancy, DELETED status, security facts, or user content. Log desensitization rules add key and value patterns such as phone/e164/otp/code/verification grant/provider payload.

## Risks / Trade-offs

- [Risk] Short code verification codes are prone to credential stuffing or SMS bombing → Multi-dimensional Redis rate limiting, short TTL, attempt upper limit, resend cooling, unified response and provider cost threshold are jointly limited.
- [Risk] Redis verification succeeds but PostgreSQL commit fails causing indeterminate status → Use short-lived, request-bound verification grant, database failure allows the same command to be retried within the grant period, and compare-and-delete on success.
- [Risk] Loss or direct rotation of mobile phone number HMAC pepper will make it impossible to find the identity → Configure startup verification, independent secret management, hash version and explicit dual version migration, and prohibit in-place rotation.
- [Risk] Account account deletion spans room, social and real-time status, partial failure may leave visible relationships → Core qualifications are invalidated in the same database transaction, external actions are only retried through durable outbox/maintenance, all entries are continuously verified `ACTIVE`.
- [Risk] Retaining identity occupation and user content after deleting the account will increase privacy obligations → only expose minimal restricted queries, clearly no public access, and the deadline and deletion method will be determined by the next data governance change.
- [Trade-off] Login identity conflicts between two existing accounts will not be automatically merged → Return to explainable conflicts to avoid irreversible business data migration; when merging is required, additional changes will be created with re-authentication of both parties, conflict rules and rollback.
- [Risk] The local fake provider passes but the real SMS or OAuth configuration is not available → real number, Google, WeChat smoke as independent acceptance tasks; when credentials are missing, the mark is BLOCKED and cannot be declared available for production.

## Migration Plan

1. Add `PhoneIdentity`, `AccountLifecycleCommand`, `User.deletedAt` and unique indexes; historical users remain in their original state, and existing OAuthIdentity and session data are not overwritten. Testing with historical database migration to prove that old OAuth logins and refresh still work.
2. Deploy API/worker and keep the mobile phone number function switch off; configure hash pepper, Redis, SMS provider, region and quota and run readiness, fake adapter, real provider sandbox and OpenAPI drift checks.
3. Open OTP request/login first, then open logged-in binding; monitor sending failure, verification failure, current limit and cost, but the diagnosis must not include the complete mobile phone number or verification code.
4. After the convergence runtime in room/social/outbox is passed, account account deletion and background restricted query are enabled; execution of event rooms, future reservations, friend invitations, restricted users and provider failure smoke.
5. When rolling back, first close the new OTP/binding/account deletion entrance, retain the new table, mobile phone number summary occupation, deletedAt, command, audit and completed account deletion fact; roll back to still press `User.status` to reject compatible binaries for non-ACTIVE accounts. You must not change `DELETED` back to `ACTIVE` or delete identity/security facts in an emergency rollback.

## Open Questions

- The production SMS provider, supported region, sender/template, cost threshold and real device number are determined by the deployment environment, as long as the adapter, privacy, error and acceptance contracts of this design are met.
- The final retention, anonymization and physical deletion period of various persistent data of the canceled account will be left to subsequent operations and data governance changes; the immediate access blocking and restricted read boundaries of this change will not be changed.
