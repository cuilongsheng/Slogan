## Goals / Non-Goals

**Goals:** Google native SDK's one-time server authorization code to the existing redemption interface; Mac browser preview uses Google Web code popup to access the same redemption interface; protected native session recovery/refresh and data entry; three CEFR intervals are consistent in the front end, API, and persistence layers; clear blocked avatar upload and WeChat code scanning.

**Non-Goals:** does not fake QR codes, does not create fake remote avatar URLs, does not implement password/email processes, and does not refer to local builds as real providers or physical device acceptance.

## Decisions

1. Google no longer uses the generic `slogan://` as the Google authorization fallback because Google has stopped supporting arbitrary custom URI schemes. Use the native Google Sign-In SDK to obtain a one-time server authorization code; the Web/iOS client ID exposed by the client is read from `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` and `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`, and the iOS URL scheme is generated from the iOS client ID. The backend only accepts `slogan://oauth/google/native` in the whitelist as the native code mode mark of this API. When exchanging tokens with Google, an empty redirect URI is passed; the secret is only reserved for the backend. This mode manages authorization bounce by the SDK and does not expose the provider secret to the client. The backend uses Google public key to verify the ID token signature, audience, issuer and expiration time. The page prompt is unavailable when there is no configuration; Expo Go does not contain native modules, and device acceptance requires development and construction and real Google configuration.
2. WeChat code scanning does not currently expose clickable fake QR codes. The entrance display is temporarily unavailable. The frame will be accessed after the actual scan code creation/status polling contract is completed. The existing `wechat/exchange` in the backend only consumes external authorization codes and does not provide a QR code life cycle.
3. The secure storage only saves the backend token pair; the access token is refreshed before expiration, and the same process refreshes alone. The rotated refresh token is first written to the secure storage and then used for subsequent requests. 401 or invalid refresh cleanup session; network error retains token and allows retries. When logging out, the backend is called first, and the local is cleaned up last; when it fails, the local is still cleaned up and the server is prompted to cancel the unconfirmed request.
4. The route is based on the onboardingState of the server `/v1/me` to enter the login, profile, age-restricted or qualified placeholder entrance. You cannot enter future room routing when the data is not completed; the age limit is only determined by the status of the server.
5. CEFR adds three values ​​`A1_A2`, `B1_B2`, and `C1_C2` to the profile contract, and the UI displays the en dash interval. The original six values ​​are still read/write to protect older clients. Prisma `CefrLevel` enumeration only appends values ​​and does not rewrite historical data; room DTO/policy continues to only allow single-level values ​​to avoid this change from changing room filtering semantics. The current API uses NestJS code-first, regenerates `openapi/openapi.yaml`, then generates the client type, and does not maintain the handwritten second contract.
6. Adding interaction to Figma avatar requires an upload interface, which is currently not available. A valid HTTP(S) avatar from Google suggestedProfile can be used for pre-filling; if the avatar is missing, the data will be left unfinished and it will be explained that it is temporarily unable to continue, and the placeholder URL will not be submitted. User allows avatar upload to remain blocked in this change. `city` corresponds to the location text in the basic information to avoid treating the free text as the ISO nationality code; record visual copywriting differences. The six options of the interest UI are mapped to stable lowercase code.
7. User-visible text is concentrated in Chinese and English resources on the mobile terminal; when the device language is Chinese, the default is Chinese, and the rest defaults to English. Use lightweight local dictionary and do not copy API DTO. The page component is only responsible for form interaction; the network and session are in the feature/service layer.
8. The development browser preview uses a 390×844 canvas. The popup code model of Google Identity Services obtains a one-time authorization code. The client only holds the public Web client ID and submits the authorization code and browser origin to `/v1/auth/web/google/exchange`. The backend whitelist and Google code exchange both use the same origin, and the backend continues to store the client secret and verify the ID token. When the browser OAuth is successful, the backend sets the `HttpOnly` and `SameSite=Lax` refresh cookies that are limited to the authentication path; production HTTPS uses `Secure`. Web access token only stores in memory. Refresh the page and call the dedicated browser refresh interface to restore the session. Exit the interface to clear cookies and cancel the server session; the native SecureStore process remains unchanged. The browser cookie endpoint verifies the source and uses credentialed CORS, and does not write the refresh token to the browser's normal storage. `sessionStorage` on the same tab page only saves the Google name/avatar suggestions bound by the platform userId so that it can continue to be prefilled after the first profile page refresh; the account does not match, the session is invalid, or it is deleted when exiting, and the token is not saved. The button is always clickable. When the configuration is missing, a clear error will be displayed when pressed, and the login success will not be faked. This preview is not a standalone web product and does not replace native device verification.

## Risks / Trade-offs

- [Real Google Web/iOS/Android configuration or native development build is not ready] → Keep configuration error state; acceptance mark `BLOCKED`, no simulation token is injected.
- [Avatar upload contract missing] → Google avatar pre-filling can complete the information of some users, and the remaining users will remain `PROFILE_REQUIRED`; this batch will not be marked as fully completed.
- [WeChat design only has static QR] → Do not treat static images as real scanned codes; the front-end entrance mark is blocked, and it is clear that subsequent QR code creation, expiration and polling contracts are required.
- [The new enumeration value affects the old version] → The backend only adds, the old six values ​​​​continue to be accepted; the release order is migration/backend/contract first, and then the mobile end. When rolling back to the mobile or server version, the enumeration expansion and existing interval data are retained; if the data must be shrunk, it must be migrated according to explicit mapping first, and PostgreSQL enum values ​​cannot be deleted directly.
- [Session refresh failed or concurrent requests] → Solo refresh and error offloading, test rotation, invalidation, network retry and logout.
- [Web pop-ups blocked, Google origin/backend whitelist inconsistent, or local OAuth credentials missing] → Display cancellation/failure/configuration error; local session not established. The preview implementation can be rolled back independently and does not involve database migration or native login protocols.
- [Browser cookies are abused by cross-site requests or remain after exiting] → Only the configured Google Web origin is allowed to use cookie endpoints. Cookie restrictions are `HttpOnly`, `SameSite=Lax`, and authentication paths. When the browser exits, clear cookies first and revoke the server session; when rolling back, close the browser cookie path and clear cookies with the same name, without changing the native token protocol or database.

## Migration Plan

First apply the append-only PostgreSQL enumeration migration, then publish the backend that accepts the old and new values ​​with code-first OpenAPI, and finally publish the generated client and mobile version. Old data does not need to be rewritten. Preserve new enumerations and data when rolling back a client or backend; old backends may reject new values, so new client writes must be stopped or compatibility processing must be maintained before rolling back the backend.
