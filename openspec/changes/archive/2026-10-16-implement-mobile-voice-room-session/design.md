## Context

The current mobile terminal has delivered the list, details, passwords, rules and device check pages with qualification gates; the device page has not submitted membership yet. `openapi/openapi.yaml` Join, short-lived credentials, member list, leave and end interfaces defined. Figma Desktop Bridge's voice room V2 `115:1425`, reconnection `114:2511`, end `114:2512` are visual basis. The backend LiveKit configuration exists in the local environment, but there is no evidence of dual-device audio for this batch.

## Goals / Non-Goals

**Goals:**

- Clients calling existing services using only current OpenAPI generation types are able to establish, resume and terminate real sessions from confirmed entry preparations.
- Web and iOS/Android share business status and interface, real-time media uses adapters for each platform; the sound is muted by default when entering the room.
- Driven seat, room host, microphone, talk and reconnect display with real members and connection events.

**Non-Goals:**

- Do not implement room creation, invitation, kicking, handover selection, extension, translation, AI assistance, chat or voice processing on the mobile terminal; corresponding V2 controls must not pretend to be available functions.
- No new or rewritten backend room models, database migrations, or second API contract.

## Decisions

1. **API first submits membership, then obtains real-time credentials, and then connects to the media.** A unique OpenAPI contract generated by reusing existing NestJS code. Membership is generated only when the user presses "Enter Voice Room"; when refreshing, read the details of `currentMembership` first, and if it is valid, directly obtain the new voucher. Compared with pre-occupying the space during equipment check, this can prevent users from occupying the capacity before entering the room.
2. **Platform isolation media implementation.** Web uses `livekit-client`; the native side uses LiveKit React Native SDK, WebRTC native dependencies and Expo config plugin to build development build. `media.web.ts` is loaded separately from the native default entry `media.ts` to prevent native modules from polluting the Web bundle. LiveKit official Expo quickstart explicitly requires development build, Expo Go cannot run the native SDK.
3. The **Credentials and passwords are only stored in short-term memory.** component holds credentials with the room session state; it is released immediately when leaving, ending or logging out. The UI and error log only use stable error codes, and do not print credentials, passwords, or complete provider error objects. Session refresh re-obtains short-term credentials from the server.
4. **Member business facts and media signal sources are merged.** `GET members` provides nickname, CEFR, order, room host and membership life cycle; LiveKit participant identity / track event provides online and speaking status. Re-pull API before connection, member change and re-entry; regular low-frequency refresh to prevent missed events. The photo avatar in the original manuscript displays the initials of the nickname when the API is not provided.
5. Retry and "exit the room" are retained when **Placeholder after failure is converged by explicit operation.** successfully joins and obtains credentials or fails to connect; exit `expectedCredentialVersion` that calls `POST leave`, even if the provider status is `PENDING`/`UNAVAILABLE`, the local connection will be disconnected as long as the business has been submitted LEFT/ENDED. When the exit request itself fails, the unconfirmed status is displayed and retry is allowed. It cannot be pretended that the seat has been released.
6. **Page recovery and final state.** Reread from the server when the room route is rebuilt. If it is still ACTIVE, get new credentials; when the server returns ended/removed/restricted, disconnect the media and go to the end or error page. The Figma reconnection status and exit entrance are displayed when the SDK automatically reconnects, and cannot be reconnected indefinitely after the certificate is revoked.

## Risks / Trade-offs

- [Expo is compatible with LiveKit native version] → Fixed compatible version, verified iOS/Android native configuration and build; passing web test cannot replace development build.
- [The user joins successfully but the provider is unavailable and the seat is still occupied] → Display the server ACTIVE fact and retry/exit; explicitly call leave and record the unconfirmed exit status to avoid silent legacy.
- [Network reconnection occurs at the same time as server removal and room host handover] → Members and details are reread each time they are reconnected, with server status taking priority; local old language/role status is not used as the basis for authorization.
- [Figma avatar and some room entrances do not have a contract] → Only display the information provided by the contract and mark the gap in the acceptance report; disable undelivered entrances.
- [Lack of evidence for Cloud device and two-player audio] → Record the local build/simulation connection and the listening and speaking acceptance of two real devices separately, and those that are not implemented are marked `BLOCKED`.

## Migration Plan

1. Connect the button after the original device page is completed to the new route, retaining the existing qualification gate; refresh the old browser to restore the server membership, and do not rely on migrating local drafts.
2. Install and fix the Web/native SDK and Expo plugins, and complete the Web/iOS/Android build verification; no database migration or OpenAPI modification is required.
3. If the native connection is blocked after going online, you can roll back the mobile version to the pre-move-in page; the created membership will still be converged by the existing leave/expiration process on the backend, and the database or server room status will not be rolled back. Confirm that the online user has exited and disconnected from the provider before rolling back.
4. Use two real qualified accounts and two devices to check mute, two-way audio, disconnection, exit and room host end during acceptance; before this, only local implementation and construction are marked.
