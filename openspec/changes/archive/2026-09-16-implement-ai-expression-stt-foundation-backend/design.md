## Context

See `proposal.md`’s Why. The existing NestJS modular monolith has authentication, profiles, room memberships, security restrictions, PostgreSQL, Redis/BullMQ, structured logging, and code-first OpenAPI, but no AI/STT provider, temporary audio portal, consent facts, or usage ledger. `voice-session` currently explicitly does not record and does not enable persistent room STT; this design only adds short requests initiated by the user and does not change the LiveKit room media path.

## Goals / Non-Goals

**Goals:**

- Provides retryable text/short speech expression assistance without persisting the original text, audio or complete transcription.
- Break room qualifications, consent, quota, provider, timeout, result verification and cleanup into testable boundaries.
- Use a separately configured replaceable AI/STT adapter and let credential-free local testing be done through a fake provider.
- Keep PostgreSQL as the source of truth for requests, consents, and usage; Redis is only responsible for short-term frequency, concurrency, and cleanup scheduling.

**Non-Goals:**

- Does not subscribe to room audio from LiveKit, does not create recording, continuous transcription, sensitive words, or post-meeting keyword pipelines.
- Does not provide AI history lists, audio playback, transcribe reading, speech synthesis, or broadcasting results to the room.
- Don’t pass off supplier sourcing, cross-border legal judgments, or privacy policy releases as code-solved problems.

## Decisions

### 1. The `assistance` module owns the business process, and the provider maintains port isolation

Added `modules/assistance`, which has express request, consent, quota, idempotent and HTTP contract. domain ports define `ExpressionGenerator`, `SpeechTranscriber`, repository, short-term coordination and cleanup scheduling; `infrastructure/ai` and `infrastructure/stt` implement provider adapter. The controller only handles authentication identities, JSON/multipart DTOs, and result mapping, and does not directly access Prisma, Redis, or external HTTP.

`RoomsModule` provides a read-only assistance context through the public application API: locking or consistent reading of room status, caller membership, room theme and user CEFR, and reusing account, age and current security restriction judgments. `assistance` can rely on the public boundaries of rooms, and rooms do not rely on assistance in reverse, avoiding circular dependencies.

The alternative is to put the AI ​​process into the voice module; reject this option because Expression on Demand neither issues real-time credentials nor controls LiveKit, and subsequent text entries also do not rely on real-time media.

### 2. Public API separates JSON text and multipart audio entry

Add the following authentication entrance:

- `POST /v1/rooms/{roomId}/expression-assistance/text`：JSON `{ clientRequestId, text }`。
- `POST /v1/rooms/{roomId}/expression-assistance/audio`: multipart containing `clientRequestId`, `noticeVersion`, `noticeConfirmed=true`, optional `sourceLanguageCode` and a single `audio` file.
- `GET /v1/me/speech-processing-consents`: Returns my current purpose, version, status and time.
- `PUT /v1/me/speech-processing-consents/ai-expression`：JSON `{ clientRequestId, action: ACCEPT | REVOKE, noticeVersion }`。

Both expression entries return the same controlled structure: request identification, main expression, zero to two `{ text, tone }` optional expressions, stable prompt identification, generation time and result expiration time. The client does not pass topic, CEFR, target user, system prompt or target language; V1 is fixedly generated by the server in English.

Audio is limited to 5 MiB at the multipart parser layer and uses the MIME allowlist, and the adapter returns the actual duration before executing the 30-second upper limit; over-limit audio may have generated STT provider usage, but will never enter expression generation. The Node process only uses the capped memory buffer and does not write temporary files, object storage or queue loads.

### 3. Request state machine to separate persistent facts from external calls

`AiExpressionRequest` uses the `(userId, clientRequestId)` unique constraint and saves `roomId`, `TEXT | AUDIO`, input SHA-256 digest, status, processing stage, lease, provider class, size/duration, minimum usage, normalization errors, structured output, and `outputExpiresAt`. Original text, audio, or transcription not saved.

The status advances by `RESERVED -> STT_RUNNING -> AI_RUNNING -> SUCCEEDED | FAILED | UNCERTAIN`. Create/replay requests and credit reservations are done within PostgreSQL transactions and actor-scoped advisory locks; external HTTP does not occupy database transactions. Each executor holds a time-limited lease and a random token. Only the current token can submit stage results to avoid late responses from overwriting the new state.

Successful requests for the same digest are directly replayed within the output retention period; `RESULT_EXPIRED` is returned after output cleaning and is not automatically regenerated. Determine the failure to replay the original failure with the same identification, and the user needs a new identification to actively retry. An unexpired lease returns `IN_PROGRESS`; recovery after lease expiration can continue or converge to `UNCERTAIN`. The adapter transparently passes the request ID as the idempotent key when the provider supports it, but the system explicitly does not promise the external provider to execute exactly once.

The alternative is to put the entire request into BullMQ for asynchronous processing; this option is rejected because the queue must not carry the original text, audio, or transcription, and the short audio cannot be safely restored if it is lost. Synchronous, time-bound provider calls are more in line with the behavior of "active request, instant expression".

### 4. Agree to use append events and current projection

`SpeechProcessingConsentEvent` saves the user, purpose, `ACCEPT | REVOKE`, notice version, provider category, server time and `(userId, clientRequestId)` idempotent facts. The current state is projected by the latest event for the same user/purpose; notice version changes will invalidate old acceptances. This table does not save audio, transcription, device information, or IP.

The audio portal requires both the currently valid `AI_EXPRESSION_AUDIO` consent and this time `noticeConfirmed=true`. Text portal does not read voice consent. Subsequent room security STT can add independent purposes and cannot reuse the AI ​​short voice consent silent authorization to continue room processing.

### 5. PostgreSQL ledger control quota, Redis only controls short-term rate

`AiUsageLedger` uses request, user, provider, capability, UTC quota day record reservation and actual unit, and the request is unique to avoid repeated deductions due to replay. The user's daily requests/audio seconds and the platform's daily budget are atomically reserved with database time and advisory lock before the provider is called; they are finally updated based on the tokens/audio duration returned by the provider, and the unknown cost protects the budget according to the reservation upper limit. The provider usage is not written due to failure of pre-qualification or parameters.

Redis Lua/atomic counter limits number of requests per user minute and number of simultaneous requests and returns `retryAfterSeconds`. New AI/STT requests fail closed when Redis is unavailable, existing rooms, departure rooms, and LiveKit media are not affected. Quotas, budgets, and default values ​​all come from ranged configurations; testing uses small quotas to verify boundaries, and production values ​​are configured by operations.

### 6. The first provider uses a compatible HTTP adapter, but the business contract does not depend on the manufacturer.

AI and STT configure provider name, HTTPS base URL, model, API key, timeout, region, purpose, maximum retention seconds and no-training/deletion mode respectively. The first implementation uses OpenAI-compatible text generation with audio transcription HTTP contract and Node built-in `fetch`/`FormData`, not allowing SDK types to enter the domain. The two base URLs, keys, models and enable switches are independent, allowing separate replacement in the future.

production only accepts HTTPS; test allows localhost. Redis, AI configuration, and policy-compliant provider declaration are required when enabling expressions; STT configuration is also required when enabling audio. The maximum claim retention period exceeds 604800 seconds, no-training is false, STT has no delete/no retention mode, or startup verification failed when credentials are missing. The log only records the provider category, not the URL query, key or original response.

The alternative is to directly rely on a single vendor SDK; reject this option because it will couple business errors, usage and data policies with SDK types, and will not be conducive to the use of different providers for subsequent room STT.

### 7. Fixed prompt template and strict output verification control result boundary

The prompt generated by the server only includes the user's current input or temporary transcription, room topic, user CEFR, target English and structured output constraints, and does not include other member information. User content is treated as a data segment and cannot override system constraints. The adapter uses strict schema verification after returning: one primary, up to two alternatives, allowed tone enumeration, each length limit and total output limit; invalid results are directly normalized to provider-response failure, the original content is not transparently transmitted to the client, and the second provider is not automatically called.

The short speech transcript only exists in the application call stack, and the reference is released in the `finally` path; the expression response does not return transcript. JavaScript cannot promise to physically erase process memory, so the acceptance only states "not writeable for persistence and unreadable" and does not claim to be able to prove that the memory is destroyed byte by byte.

### 8. Private output uses short TTL and resumable cleanup

Structured output is retained for 24 hours by default, configurable from 5 minutes to 7 days. A successful transaction simultaneously writes `outputExpiresAt` and submits the `EXPIRE_AI_OUTPUT` BullMQ job without content; the job is updated with database time execution conditions, the text is blanked, and `outputPurgedAt` is recorded. When the worker restarts, it scans the record reconstruction task that has expired but still has the text, and repeatedly cleans up the idempotent. Redis loss only delays cleanup scheduling, database scans eventually converge; exposed expiration semantics must not be extended, reads are considered expired immediately after `outputExpiresAt`.

Do not add the cleaning job to the command union of the existing room realtime queue, but add an independent assistance maintenance queue to avoid room timing and AI data management blocking each other.

### 9. OpenAPI continues to be generated by NestJS code-first one-way

DTO and Swagger metadata describing JSON, multipart, file size/MIME, consent entry, unified results, 429/503/conflict and expiration errors; `openapi/openapi.yaml` remains the only release contract. Can’t write the second schema by hand. HTTP/structured log desensitization is added to the request body, multipart metadata, Authorization, input summary, provider response and result body; the minimum indicators are aggregated by status, stage, provider category, time consumption and usage.

## Risks / Trade-offs

- [Risk] Provider may have completed and billed after external timeout, cannot guarantee exactly-once across vendors. → Uses lease, provider idempotent key (if supported), `UNCERTAIN` state, and single platform budget reservation; no automatic concurrent retries.
- [Risk] Multipart memory upload may increase process memory pressure. → parser limits single file to 5 MiB before allocation, one file per request, limits concurrency; stops new audio requests if Redis coordination is unavailable.
- [Risk] STT can only confirm the true duration after being parsed by the provider. Extra-long audio may incur an STT cost. → Limit the number of bytes, the client recording upper limit and the provider return duration at the same time; overly long results will not be entered into AI generation and actual usage will be recorded.
- [Risk] Supplier statement does not equal proof of true deletion. → Configuration and code only prove the enablement threshold; real smoke, supplier policy/region/deletion proof are recorded separately, and when evidence is missing, it is marked as BLOCKED.
- [Risk] PostgreSQL daily quota lock creates hot spots under high traffic. → V1 uses actor/day and platform/day advisory keys on a small scale; indicator display lock waits before considering independent metering service.
- [Risk] Temporary output text will still be in the database in TTL memory. → Shortest configurable TTL, personal isolation, no list entry, log desensitization, immediate invalidation of expired reads and recoverable physical blanking.
- [Risk] Redis failure will make AI temporarily unavailable. → Select fail closed to prevent unbounded concurrency and runaway costs, while keeping the live voice in the room completely independent.

## Migration Plan

1. Added forward-only migration of enums, `AiExpressionRequest`, `SpeechProcessingConsentEvent`, `AiUsageLedger`, and constraints/indexes; verified empty databases with isolated schema vs. history chain upgrades with existing user, room, security, and social data.
2. Deploy the assistance module, fake/provider contract tests, consent and text/audio portals, and independent maintenance queue that are turned off by default; when not enabled, the portal returns stable and unavailable results.
3. Enable after configuring the AI/STT provider, Redis, quota and retention that comply with the policy; use synthetic text and impersonal short audio to perform real smoke, and do not write the key and original provider content in the repository or acceptance document.
4. Observe timeouts, failure rates, quotas, budgets, and cleanup delays; only record the true provider acceptance as PASS after the provider connection, data policy, and cleanup evidence pass.
5. When rolling back, first turn off the assistance enable switch and stop new requests, and then roll back the application. Keep new tables, usage, consent and minimum request facts; continue running or manually perform body cleanup without destructive down migration.

## Open Questions

- The final production provider, zone, and model names are determined by the deployment configuration; the selection will not change this design as long as the current public contract and data policies are met.
- The public beta day quota, platform budget, and private output TTL in the range of 5 minutes to 7 days are determined by operations before activation, and the default values ​​are not considered long-term commitments.
