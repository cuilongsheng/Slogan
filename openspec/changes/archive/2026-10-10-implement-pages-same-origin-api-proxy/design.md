## Context

Both Admin and Expo Web clients require an absolute API base URL, and the interface path comes with `/v1`. The existing BrowserAuthController verifies that the original Origin belongs to both CORS and Google allowlist, and requires Google redirectUri to be equal to Origin; the production refresh cookie is HttpOnly, Secure, SameSite=Lax, Path=/v1/auth/web, and no Domain. Cross-site between Render and Pages, using the same origin proxy for each site.

## Goals / Non-Goals

Goal: Two-site build reproducibly generates the same Worker and API route, preserving bytes, status codes, session and origin security boundaries. Non-target: visual/business authentication changes, open registration, native application proxy, external resource or real provider acceptance, scheduling recovery.

## Decisions

- `scripts/pages-api-proxy.mjs` is a dependency-free Worker source. The build copy is `_worker.js`. `_routes.json` only includes `/v1` and `/v1/*`; the rest of the requests are handed over to ASSETS. Use official advanced mode without external `_redirects` redirection.
- `API_UPSTREAM_ORIGIN` is configured for Pages runtime and only accepts single-tier `https://*.onrender.com` origin or approved `https://slogan-api-pi.vercel.app` without credentials/path/query/fragment/non-default port. Guest cannot specify target, configuration error immediately 503; static page still available. The latter comes from the Vercel routing correction that has been incorporated on 2026-10-07. When archiving, it is synchronized with the current code and release records; no Vercel projects are released.
- The public API base corresponding to `build:pages:admin` and `build:pages:mobile` verification is a complete HTTPS origin, and values ​​with `/v1` or paths are rejected. The public API base must fill in the respective stable Pages origin; turn off dotenv automatic loading during construction, and verify the product after copying the Worker and routing. The upstream is runtime configuration and is not written into the browser bundle.
- Original method, query, request body flow, Origin, Authorization, Cookie retained; removed hop-by-hop and its Connection declaration fields, Host, content length and client forwarding/IP header. The trusted proxy and rate limiting configuration of the API are not relaxed; when the trusted proxy is not configured, the current is still limited based on the connection IP, and the quota may be shared. The real client IP attribution needs to be verified when publishing the actual chain, and any X-Forwarded-For is not allowed.
- The request uses no-store, the response is overridden to private, no-store, and the entity cache verification header is removed. Credentials not read or printed, request/response not logged. The 90-second first packet cutoff allows Render to cold start; network failure 502, cutoff 504, no retry to avoid repeated POST. Render HTML availability page to masked JSON (preserve 5xx, return 502 for exception 2xx/4xx HTML). The return stream is not buffered. After the response has been sent, the body interruption is sensed by the browser and the status cannot be overwritten; HEAD/204/304 has no body.
- Handle redirection manually, do not send Cookie/Authorization to any redirection target; only allow fixed upstream or API Location of this website, rewritten to origin of this website. External domain, non-API, non-HTTP(S), location with credentials failed and closed with 502. The existing API does not have endpoints that require cross-origin redirection.
- Set-Cookie uses Workers getAll or Node getSetCookie to read/append in strips, never split by commas. Existing host-only cookies are retained as is; any Domain attribute is rejected to prevent upstream domain cookies from silently invalidating or expanding their scope in Pages. Do not change Path, SameSite, Secure, HttpOnly, Expires; multiple Cookies and clear semantics are retained.
- The API contract has no schema changes and remains the only OpenAPI without introducing a second copy. Redis is only updated to the Upstash free candidate and native TLS REDIS_URL; the client is not changed, the remote credentials are not verified, and the free quota is not guaranteed to carry continuous BullMQ polling.

## Risks / Trade-offs

The new Worker forwards the authentication credentials to the only configured Render upstream. The configuration needs to be only for the controlled service; the TLS domain name cannot be used to prove resource ownership. A proxy failure will cause both web APIs to fail. Pages/Workers free quota, Render cold start, Neon calculation time and Upstash command quota still require public network evidence. Upstash may have BullMQ command traffic even when the queue is idle and cannot commit to budget or reliability based on compatibility.

## Migration Plan

No database migration. Five accounts are required to change and merge into main separately. When creating Pages, fill in the respective public base/Google client, API_UPSTREAM_ORIGIN when running; the CORS/OAuth allowlist of the API contains two stable origins. The temporary preview domain is not automatically authorized. Verify the actual address and complete the independent online account initialization before publishing; this round will not be executed.

The rollback must simultaneously roll back the web product and the public/runtime configuration to the verified version; retain the same-origin authentication topology, and cannot point the old static product directly to the cross-site Render to claim that the session is normal. Disable the web portal and return to maintenance status when there is no verified version. Upstream/API/database rollback is independent and does not delete or copy account data.
