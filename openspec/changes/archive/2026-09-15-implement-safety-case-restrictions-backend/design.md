## Context

See [proposal.md](./proposal.md) for demand motivation. Currently `moderation` writes `Report` and the corresponding `RoomEvent` in a PostgreSQL transaction, but there is no follow-up case; `backoffice` has provided persistent multi-role, current role verification, role modification idempotent and administrator set transaction locks; `audit` has provided append-only background auditing. Instant rooms, reserved rooms and real-time vouchers are checked separately in their respective transactions `User.status`, and there is no unified temporary restriction fact.

This change is a Level 2 security and extensive schema change. It spans report acceptance, backend authorization and auditing, user status, instant/booked rooms, and real-time credentials. PostgreSQL must continue to be the persistent source of truth for cases and restrictions; Redis/BullMQ can only accelerate expiration and reallocation, not decide whether a user remains restricted. The only API contract continues to be deterministically generated by NestJS code-first to `openapi/openapi.yaml`.

## Goals / Non-Goals

**Goals:**

- Atomic creation of one-to-one cases, initial assignments, participant snapshots, processing activities, and necessary audits without unbundling existing reporting transactions.
- Implementing retryable human case processing with explicit state machines, current roles, and database concurrency control.
- Make all existing room write entries use the same temporary limit judgment within their respective database transactions, and handle boundaries in database time.
- Make temporary restrictions, appeals, early liftings, automatic expirations, and permanent bans with unlosable facts, stable idempotent results, and minimal responsiveness.
- Provide deployable backfill for historical reports and retain data compatibility for application rollback.

**Non-Goals:**

- Does not abstract security handling into a common rules engine, nor does it have pre-built STT, user blocking or room disabling providers.
- Do not allow background tasks to actively modify LiveKit rooms or revoke issued credentials; the processing of active rooms is left to the room security action change.
- Do not create editable evidence documents or copy complete business data; evidence packages are read-only projections of facts allowed.
- Figma, visual or equipment acceptance materials will not be produced for this pure backend change.

## Decisions

### 1. Create a new `safety` business module, and the report acceptance is still owned by `moderation`

The `safety` module has case, assignment, limit, appeal, recovery runner, background controller and personal limit controller. `moderation` maintains the report verification and acceptance entry, and calls the safety persistence helper without dependency injection in the existing `PrismaReportRepository.submit()` transaction, writing cases, participant snapshots, initial activities, and system audits. This helper accepts an existing Prisma transaction client and does not open transactions on its own.

This can keep "report + RoomEvent + case" all or nothing, and also avoid `ModerationModule` and `SafetyModule` from importing each other. Another solution is to publish a queue event to create a case after the report is successful, but it will cause the status of accepted reports with no cases temporarily or permanently, so it is not adopted.

### 2. Use a standardized relationship table to save facts and an activity table to save case processing tracks.

Add the following persistent types:

- `SafetyCase`: `reportId` unique, saves room, target user, status, current handler, processing time, evaluation level, final status type, final status reason, version and timestamp.
- `SafetyCaseParticipantSnapshot`: Save the member ID, role, life cycle and existing time fields that are visible when accepting reports, to avoid subsequent re-adding the context required to cover the case.
- `SafetyCaseActivity`: Add creation, allocation, reassignment, receipt, start and final actions for case processing records.
- `SafetyRestriction`: Save the unique final disposition of the case, `TEMPORARY` or `PERMANENT` type, level, start/end, early release, expiration projection and decision maker.
- `SafetyAppeal`: Each temporary restriction can contain up to one temporary restriction, saving the user reason, deadline, `PENDING/UPHELD/LIFTED`, processing reason and processor.
- `SafetyCommand`: Uniquely save actions, normalized request hashes, and minimum result snapshots as `(actorUserId, clientRequestId)`, providing independent idempotent ledgers for cases, restrictions, and appeal orders.
- `SafetyAssignmentState`: Singleton saves the rotation cursor for parallel load distribution.

Case status is `OPEN -> UNDER_REVIEW -> RESOLVED|DISMISSED`. Unassigned is `assigneeUserId = null`, do not add `UNASSIGNED` status that is duplicated with the case status. The evaluation level is only written when the final decision is made; there is no penalty or rejection and no falsification of the risk level. The restriction status field is a projection to facilitate querying, and the actual validity is still determined by the type, `startsAt`, `endsAt`, and `liftedAt`.

Use relational columns instead of cramming evidence, commands, and activities all into JSON to facilitate the creation of unique constraints, foreign keys, and filtered indexes. JSON only allows fixed whitelist small fields used for idempotent results and audits, and cannot save the report text or evidence package.

### 3. Calculate minimum load and serialize rotation in database transactions

When creating cases and restoring allocation, first lock the `SafetyAssignmentState` singleton, and then query the safety officer whose account is `ACTIVE`, whose role has not been revoked, and the number of assigned cases of `OPEN/UNDER_REVIEW`. First select the minimum load set, then select one person from the stable `userId` sequence after rotating the cursor and update the cursor. Leaves empty handlers and unassigned activities when there is no safety officer.

Resume scanning handles two types of cases: open cases for which the current handler is no longer available, and open cases for which no handler is available. It reuses the same lock and selection algorithm, and rechecks the case status and current role for each transaction, so multiple instances and repeated runs will not produce two current handlers. Allow the safety officer to pick up cases that have not yet been allocated through compare-and-set; only one update is successful when automatic allocation and picking are concurrent.

Although it is certain to select the minimum value by just `userId`, it will continue to favor the same safety officer; random selection is difficult to reproduce and test, so it is not used.

### 4. Permissions are determined by coarse-grained guard and service layer resource scope.

Extended background permissions include full case reading, case work, restricted work and appeal work:

- `PLATFORM_ADMIN` gained full read-only access to the case and evidence.
- `SAFETY_OFFICER` Gain own case/unassigned case read, case work, restricted work, and appeal work permissions.
- The union of permissions takes effect when holding two roles at the same time; no role implies another role.

guard reads the current PostgreSQL role through the existing `BackofficeService.authorize()` each time; the service layer again constrains the action by `assigneeUserId`, case status, and target resource. Sensitive query is completed in one transaction "Read Allowed Projection + Append Access Audit", no result is returned when the audit fails. The business of authenticated backend users refuses to write the minimum rejection audit, and ordinary users refuse to follow the existing boundaries based on the backend entrance.

### 5. Backend API uses resource routing and unified command envelope

New API:

- `GET /v1/backoffice/safety/cases`、`GET /v1/backoffice/safety/cases/{caseId}`、`GET /v1/backoffice/safety/cases/{caseId}/evidence`
- `POST /v1/backoffice/safety/cases/{caseId}/claim`、`/start`、`/dismiss`、`/resolve`
- `GET /v1/backoffice/safety/restrictions`、`POST /v1/backoffice/safety/restrictions/{restrictionId}/lift`
- `GET /v1/backoffice/safety/appeals`、`POST /v1/backoffice/safety/appeals/{appealId}/decide`
- `GET /v1/me/safety-restrictions`、`POST /v1/me/safety-restrictions/{restrictionId}/appeal`

All lists use opaque stable cursors composed of time and UUID, and the limit is `1..100`. Case orders use `clientRequestId`; actions requiring reasons limit reasons to 1..500 Unicode characters and appeal reasons to 1..2000 Unicode characters. `resolve` explicitly passes in `NO_ACTION`, `TEMPORARY_RESTRICTION` or `PERMANENT_DISABLE`; temporary restriction must be with level, permanent ban must be with `SERIOUS/HIGH_RISK` and `factsConfirmed: true`. The client cannot pass the duration or server time.

`SafetyCommand` Saves the normalized hash and result identifier within the business transaction. The same command returns a persistent result without recalculating the time; the same request with different hashes returns a conflict. Unique constraints and version compare-and-set handle first-time concurrency and cannot rely solely on in-process locks.

### 6. Evidence package combines immutable source and admission snapshot on read

The evidence query is based on the case, combining the original `Report`, the report corresponding `RoomEvent`, `SafetyCaseParticipantSnapshot`, the room already has `RoomEvent`, the target user's related report/case/restriction summary and `SafetyCaseActivity`. Return items with source identification and occurrence time. The collection adopts a stable order and sets a bounded quantity; the excess returns count and paging/truncation flag to avoid unbounded responses from a high-frequency account.

Report instructions only appear in authorized case evidence responses; the case list only returns summaries such as category and status. Evidence and administrative audit DTOs use explicit field mapping and do not serialize Prisma raw objects. Future STT changes can only add new minimal risk event sources to the combiner, and cannot write full transcripts to this model.

Another option is to copy the entire evidence package JSON when the case is created, but this will solidify redundant personal data, make it difficult to enforce future retention policies, and miss room events that are completed later, so it is not recommended.

### 7. Temporary restrictions are determined by the persistence time interval, and status convergence is separated from access judgment.

Temporarily restricted to using PostgreSQL `clock_timestamp()` to obtain `startsAt` within a closed transaction, and the server calculates and fixes `endsAt` and `appealDeadlineAt = startsAt + 30 minutes` based on level. The valid conditions are unified: type is temporary, `startsAt <= dbNow < endsAt` and `liftedAt IS NULL`. Multiple overlapping restrictions are all retained; the error summary returns the highest valid level and the latest `endsAt`, and the personal history returns each record.

Provides qualification query for receiving Prisma transaction client at `safety/persistence.ts`. Instant room creation/joining, reserved room creation/reservation and real-time voucher reservation must call it within the original transaction and use the same database time. There is no window of "check first, then open transaction writing" between restriction and business writing. Future room invitation capabilities must call the same helper.

Checking only in guard or Redis cache will produce bypass and expiration drift, so it is not used. Redis can cache prompt information, but cannot participate in the authorization conclusion.

### 8. The independent security queue is responsible for expiration and allocation recovery, and the database scans to find out.

Added independent `slogan-safety` BullMQ queue and `SafetyRunner` to avoid putting security operations in the voice module. Try your best to schedule expired jobs after creating temporary restrictions; application startup and fixed short-cycle scanning of expired `ACTIVE` restrictions, unassigned cases and handler failure cases in the database. job only carries kind and resource id, but does not carry report text or evidence.

The expired worker re-reads the limit through the row lock; if the database time has expired and has not been released, the projection is set to `EXPIRED`, and the activity and `SYSTEM_JOB` audits are appended. The submission penalty can still be successful when the queue is unavailable, because `endsAt` has been persisted; the request path is released immediately after reaching `endsAt`, and the state is converged after the scan is resumed. Structured logs only record fixed event names, resource identifiers and stable result codes.

### 9. Early termination and appeal share an unrepeatable termination fact

`liftedAt/liftedByUserId/liftReason`, which updates the same restriction directly in advance and passes the appeal. Transaction first lock restriction; if it has been released or expired, the existing state or stable conflict will be returned and the original decision will not be overwritten. The appeal uses the `restrictionId` unique constraint to ensure that each restriction is at most one, and uses the database time to judge `submittedAt <= appealDeadlineAt`.

Any current safety officer can view and handle pending appeals. `UPHELD` only ends the appeal; `LIFTED` ends the appeal and writes release, activity and successful audit in the same transaction. Since the product does not confirm the processing SLA, no scheduled tasks will be automatically passed or automatically rejected.

### 10. Permanently disable reusing account status and expand the last administrator transaction invariant

Permanently disposes write `SafetyRestriction(kind=PERMANENT)` and updates `User.status` to `DISABLED`, while revoking the target's unrevoked `AuthSession`. Ordinary authentication still rejects the old access token through the account status of each request; the refresh token becomes invalid due to session revocation. The active revocation and room kicking of the issued LiveKit token are not included in this change.

Permanently disable the advisory lock target user and reuse the same platform administrator set advisory lock with role modification. If the target is the last platform administrator with an available account and a valid role, transaction record rejection auditing is not disabled; concurrent role revocation and permanent disabling cannot reduce the effective administrator to zero. There is no recovery entry for permanent ban, to avoid introducing an unreviewable unblocking path when the appeal rule is not confirmed.

### 11. Backend audit and business activities bear different responsibilities

`SafetyCaseActivity` is the business processing trace visible in the case; `BackofficeAuditEvent` is the high-privilege access and operation trace that can be queried by administrators/auditors. Security action transaction writes business facts, activity, `SafetyCommand` and success audit simultaneously. Add case reading/assignment/processing, restriction creation/expiry/lift, appeal reading/submission/decision and permanent ban to the audit action whitelist; add `SYSTEM_JOB` to the actor type.

Audit `details` only saves identifying results such as cases, restrictions, appeals, status, levels, versions, etc. It does not save report descriptions, appeal text, evidence, tokens, SQL, stack or request bodies. Refuse to audit and save the stable result code independently; if the same idempotent command already exists, the original result will be reused and a second successful audit cannot be generated.

### 12. OpenAPI and error contracts remain single source

After the DTO, controller decorator and stable error mapping are completed, run the existing build script to update `openapi/openapi.yaml` without handwriting the second contract. The report response retains the original fields and adds `caseId`; security restrictions deny the use of the unified stable business code and the minimum `effectiveSeverity/endsAt` details. Verification, override, window closing, status conflict and idempotent conflict maintain stable HTTP semantics respectively, and responses and logs do not reveal internal errors.

## Risks / Trade-offs

- [Risk] High-frequency reporting may make the global allocation lock a short-term hot spot → only hold the lock during the short transaction interval for selecting handlers and updating cursors, case evidence and notifications are not executed within the lock, and the upper limit is recorded with concurrency testing.
- [Risk] Multiple room entries are missing temporary limit checks → Integrate each current write entry with a shared transaction helper and set up a set of cross-module contract tests; code search checks all member creation, reservation writing and credential reservation paths.
- [Risk] The expired projection still displays `ACTIVE`, causing background misunderstanding → All projections first calculate the effective status according to the database time, and the runner only performs final convergence; test queue shutdown and boundary time.
- [Risk] The user-visible deadline of overlapping restrictions is easy to get wrong → Valid queries uniformly return the highest level and the latest end time, and recalculate from all persistent records after removing one.
- [Risk] Permanently disabling background accounts breaks last admin protection → role revocation and disables shared advisory lock with effective admin count, and overrides cross-concurrency testing.
- [Risk] Evidence query expands sensitive information exposure → Resource range verification, fixed DTO, result cap and read auditing take effect at the same time; original ORM serialization and arbitrary JSON request snapshot are prohibited.
- [Risk] There is no handler for a short period of time after the historical report is backfilled → Unassigned cases are created first during migration, and the application starts scanning and then allocates; the unassigned status can be queried and does not affect the fact of the report.
- [Trade-off] Each reported case will increase manual repeated viewing → V1 maintains a certain one-to-one traceability relationship, and evidence shows relevant signals; automatically merges matching and mis-merging rules that require independent approval.
- [Trade-off] This change only blocks new room actions and new credentials → Users already in the room may continue until the end of the existing session; subsequent room security actions change and then define kicking and room host takeover.

## Migration Plan

1. Add safety enums, relational tables, unique constraints, foreign keys, and query indexes, and expand administrative audit actor/action acceptance; do not delete or rename existing columns yet.
2. Create a `OPEN`, unallocated `SafetyCase`, and minimal creation activity for each historical `Report` in the same migration; copy the then-available participant facts from the existing `RoomMembership` and leave the missing fields empty, without inferring historical status.
3. Run Prisma format/validate/generate and migrate smoke to verify that the number of reports is consistent with the number of cases, `reportId` is not duplicated, the foreign keys are complete and the old query still works.
4. Deploy application with new schema read and write; initiates recovery scan of allocation history and newly generated unallocated cases, and converges expiration limits. The application can still start and authorize correctly when Redis is unavailable.
5. Generate and verify a unique OpenAPI contract, run module tests, API full tests, format/dependency/contract checks, and complete runtime smoke from reports to appeals/expires of real PostgreSQL + Redis.
6. When rolling back, roll back the application code first, retaining the new tables, enumeration values ​​and backfill data; the old application can still write reports, and when rolling forward again, execute idempotent backfill again to fill in the missing cases. Cases, restrictions, appeals, or audit facts are not deleted unless otherwise approved for data migration.

This change has no UI, so there is no visual or device acceptance; the acceptance evidence consists of OpenSpec scenario comparisons, OpenAPI diffs, migration results, automated tests, and local runtime smoke. LiveKit Cloud real connection is not the completion threshold of this change, and the new credentials after the restriction refuse to pass local/pseudo-provider evidence verification before provider call.
