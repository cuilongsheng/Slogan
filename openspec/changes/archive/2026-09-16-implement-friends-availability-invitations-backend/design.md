## Context

See `proposal.md`’s Why. Currently PostgreSQL has saved users, information, rooms, membership, security restrictions and room audit facts; Redis has been used for temporary coordination, and room-level real-time presence only describes LiveKit participants and does not represent that the application user has been online recently. Existing `RoomsService.join` performs account, age, security restrictions, status, password, rule and capacity verification in the transaction of locking the room, `host-controls` alone has the re-invitation of removed members.

This change also involves new bidirectional relationships, directional blocking, temporary presence and joining transactions, and is a Level 2 architecture and security boundary change. OpenAPI continues to be generated by NestJS code-first, with `openapi/openapi.yaml` being the only publishing contract.

## Goals / Non-Goals

**Goals:**

- Express friend requests, friend relationships, user blocks, and general room invitations with unique persistent facts, and converge under concurrency and retries.
- Makes any social read and write perform blocking, account, profile, age and security restriction checks in both directions.
- Use short-term Redis signals to generate idle projections, safely degrade when Redis fails and do not affect the voice room.
- Let ordinary invitations be consumed in existing join transactions, reusing room password, capacity and membership invariants.
- Keep existing clients compatible: public/shared link join process without invitation continues to work.

**Non-Goals:**

- Private messages, group chats, following, contact import, recommendation sorting, push or email notifications.
- Modify the display rules for blocking parties in public room discovery.
- Replace the removed member `host-controls` with a normal invitation to re-invite.
- Treat Redis presence, client heartbeat, or invitations as room capacity and membership facts.

## Decisions

### 1. Relationships use normalized user pairs and explicit final states

Added `FriendRequest`, `Friendship`, `UserBlock` and `SocialCommand`. Friend request and friend relationship saved simultaneously `userLowId/userHighId` normalized user pair; request saved as `requesterUserId/recipientUserId`. The database checks that two users are different, and uses a partial unique index to ensure that one user has at most one pending request and at most one valid friend relationship. Request to use `PENDING/ACCEPTED/REJECTED/WITHDRAWN/BLOCKED`, friend relationship preservation `endedAt/endedByUserId`, block record preservation `unblockedAt`, to support auditing and idempotent result recovery.

The alternative is to store a line of friend edges for each direction. This solution would require acceptance, deletion, and concurrent retrieval to be consistent across the two lines, so it is not used.

### 2. Shield the normalized user from atomic cleaning in the lock

When creating or unblocking, the repository obtains a transaction-level advisory lock on a normalized user pair in a database transaction, and then checks and changes blocks, friends, requests, and pending invitations. Creating a block will end the friend relationship, set the pending requests from both parties to `BLOCKED`, and set all `PENDING` ordinary invitations between the two parties to `CANCELLED`. Unblocking only closes the direction initiated by the caller and does not restore any old records.

Using bidirectional read filtering is still not enough to prevent new blocks from being added after a list is read to before being written, so all friend and invite writes are rechecked within the same user pair lock.

### 3. General social command to save idempotent results

`SocialCommand` is unique to `(actorUserId, clientRequestId)` and holds the command type, normalized request summary, status and minimum result identifier. The application service first locks the command in the transaction; the same digest replays the existing results, and different digests return conflicts. The relationship records its own unique constraints as a second layer of concurrency protection. The command and domain status are submitted in the same transaction, and the log does not record the data text or the reason for blocking.

Adding request identifiers to each table cannot cover the "accept/reject/withdraw/delete" commands that act on existing records, so an independent command table is used.

### 4. Social module owns relationship and availability, Rooms module owns invitations

Added `modules/social`, which provides public application API for friends, blocking, presence and qualification query. The normal `RoomInvitation` model, repository, service and controller are located in `rooms`, because the invitation validity and consumption depend on the room's current room host, status, membership and joining transactions. Rooms one-way relies on Social's public API and the minimum qualified helper to receive Prisma transaction client; Social does not reverse import Rooms, thus avoiding `forwardRef` and circular module dependencies.

Changing the room host will not automatically invalidate the existing ordinary invitation: the invitation is a directed access prompt sent by the room, and it will still be re-verified according to the current room facts when joining. After the room enters `ENDING/ENDED/CANCELLED`, the read and consumption paths immediately treat the invitation as unavailable; background convergence can mark `CANCELLED` in batches, but the correctness does not depend on the task running on time.

### 5. The invitation does not reserve a seat, and the consumption joins the reservation transaction.

`RoomInvitation` saves the room, room host, target, `PENDING/DECLINED/CONSUMED/CANCELLED` status and time when sending. `RoomsService.join` accepts optional `invitationId`. After locking the room, it uses the same Prisma transaction client to verify invitations, two-way blocking, and target qualifications, and then performs original passwords, rules, reservation quotas, and capacity checks; the invitation is set to `CONSUMED` only after the membership is successfully created. Any check failure will roll back consumption.

Ordinary invitation is invalid for `REMOVED` membership, and will continue to return to the existing `ROOM_INVITATION_REQUIRED`, which will be restored by the dedicated process of host-controls. LiveKit tokens will not be issued for invitations; live credentials are still generated by the existing entrance to voice.

### 6. Availability is the intersection of Redis short-term signals and PostgreSQL facts

Authentication heartbeat only writes `social:presence:<userId>`, TTL is controlled by the server configuration `SOCIAL_PRESENCE_TTL_SECONDS`, defaults to 90 seconds and is limited to 30–300 seconds; the response returns the server `expiresAt` and the recommended refresh seconds. Client cannot write userId or time. The idle query first obtains qualified candidates from PostgreSQL based on user creation time and ID, excludes valid memberships, disabled/deleted accounts, incomplete/underage information and current security restrictions, and then reads Redis signals in batches and filters bidirectional blocking.

The friend list reuses the same projection and only returns `isAvailable` as an instantaneous Boolean value. The cursor is bound to the sort field and query type; when the presence changes during paging, the system ensures that the cursor is legal and the user ID does not go backwards, and does not promise to freeze the real-time state across pages.

Do not use Redis key scan to find online users because its cost and paging semantics are uncontrollable; PostgreSQL determines the candidate set, and Redis only answers whether the candidates have been online recently. heartbeat returns a stable temporary unavailability error when Redis is unavailable, and the list returns an inviteable list with an idle status of false or an empty list.

### 7. HTTP and privacy boundaries

Plan entrance:

- `POST/GET /v1/friend-requests`，`POST /v1/friend-requests/{id}/accept|reject|withdraw`
- `GET /v1/me/friends`，`DELETE /v1/me/friends/{friendUserId}`
- `POST/GET /v1/blocks`，`DELETE /v1/blocks/{blockedUserId}`
- `POST /v1/me/presence/heartbeat`，`GET /v1/people/available`
- `POST /v1/rooms/{roomId}/invitations`，`GET /v1/me/room-invitations`，`POST /v1/room-invitations/{id}/decline`
- Add optional `invitationId` to existing `POST /v1/rooms/{roomId}/memberships`

List only returns user id, public nickname, CEFR, allowed display regions/topics, and `isAvailable`; does not return birthday, session, precise time, IP, device, blocked direction, or room member details. The target is unavailable and the presence mask is uniformly mapped to a stable unavailable error.

## Risks / Trade-offs

- [Risk] If the application exits abnormally before the heartbeat expires, it will briefly appear online. → The upper limit of TTL is 300 seconds. Entering the room is immediately overwritten to idle false by PostgreSQL membership. Invitation and joining are still re-verified.
- [Risk] A large number of offline candidates can cause an availability query to scan too many database rows. → Use batched keyset query with an upper limit and Redis `MGET` to record the scan/return ratio; when the scan upper limit is reached, fewer results are returned and the cursor is continued, without full table scan.
- [Risk] Blocking concurrently with friends/invites may leave visible relationships. → Normalized user protection for advisory locks, intra-transaction qualification reviews, database unique constraints and integrated concurrency testing.
- [Risk] Rooms calling Social persistence helper may expand module coupling. → Only the qualifications and transaction helpers are exposed, and the repository is not exported; invitation ownership remains in Rooms, and dependencies remain one-way.
- [Risk] Preserving the final state of the relationship will increase the amount of data. → This change creates an index and retains the minimum fields; the specific retention/cleaning period will enter subsequent data governance changes.

## Migration Plan

1. Added enumerations, relational models, foreign keys, unique/partially unique indexes, and check constraints; empty databases and isolation schemas containing existing user, room, security, and reservation data perform upgrade verification without backfilling friends or presence.
2. Deploy read/write services, Redis presence and new HTTP entry compatible with old clients; `invitationId` remains optional.
3. Generate and check unique `openapi/openapi.yaml`, perform domain, repository, concurrency, HTTP permissions and migration tests; Redis runtime smoke verifies TTL, expiration and failure degradation.
4. When rolling back, first offline the new entry and join invitation consumption branch, stop heartbeat; Redis key automatically expires, PostgreSQL new table and data are retained for forward repair, and no destructive down migration is performed.

Product acceptance needs to cover mutual consent of friends, two-way disappearance after blocking, online/check-in/expired status switching, room host invitation to join, capacity competition and password/restriction rejection. This change does not rely on physical device push or external providers; production deployment status is recorded separately.
