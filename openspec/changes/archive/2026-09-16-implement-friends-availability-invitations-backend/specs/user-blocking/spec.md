## Purpose

Define user active blocking, two-way social isolation, and relationship cleanup boundaries so that blocked relationships cannot continue to generate directed interactions through friends, free lists, or ordinary room invitations.

## ADDED Requirements

### Requirement: Users can block other users in a targeted manner

The system MUST allow authenticated users to block another user but not themselves. The blocking fact is only visible to the initiator; repeated blocking MUST return the same valid result, and no notification of the blocker's identity or reason is sent to the target user.

#### Scenario: Create shield

- **WHEN** User blocked another existing user
- **THEN** The system saves the unique blocking fact from the caller to the target user and returns minimal results

#### Scenario: Block yourself

- **WHEN** User targeted themselves for blocking
- **THEN** The system rejects the operation and does not create a record

### Requirement: Block and isolate social interactions in any direction

The system MUST enforce two-way isolation in friend requests, friend lists, free user lists, and regular room invitations: as long as either party blocks the other, neither party can see each other's social entries, establish friendships, or send regular room invitations. The server MUST recheck masking facts in write transactions and cannot rely solely on list filtering.

#### Scenario: The blocked user directly initiates a request

- **WHEN** The blocked user bypasses the client and directly sends friend requests or ordinary room invitations to the blocked person.
- **THEN** The system returns consistent target unavailability results without exposing the shielding direction

#### Scenario: Block both parties from querying the free list

- **WHEN** Either party queries the list of friends or inviteable users
- **THEN** Neither party can see the other party’s social entries and idle status

### Requirement: Block atoms to clean up existing social relationships

The system MUST unfriend the two parties in the same persistent transaction that created the shield, terminate the pending friend requests from both parties, and cancel any pending general room invitations between the two parties. Accepted or consumed history can retain minimal auditing facts, but permissions cannot continue to be granted.

#### Scenario: Block existing friends

- **WHEN** User blocks current friend
- **THEN** Blocking, unfriending, pending requests and pending invitation cleanup all succeeded or failed

### Requirement: Unblocking does not restore historical relationships

The system MUST allow the block initiator to unblock themselves. The system shall not automatically restore old friend relationships, requests or invitations after cancellation; if both parties need to become friends again or send invitations, they MUST complete the corresponding process again.

#### Scenario: Unblock

- **WHEN** The block initiator unblocked the effective block
- **THEN** The block is invalid and historical friend relationships and invitations remain invalid.

### Requirement: Blocking operation is safe to retry

The system MUST require the creation and unblocking of UUID request identifiers generated by the caller, and ensures that retrying the same command returns the original result, and that different command reuse identifiers return stable conflicts.

#### Scenario: Concurrent duplicate masking

- **WHEN** The same user concurrently blocks the same target using the same request ID.
- **THEN** The system only saves one effective shield and one set of relationship cleaning results.
