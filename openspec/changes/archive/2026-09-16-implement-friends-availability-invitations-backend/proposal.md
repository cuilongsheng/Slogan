## Why

The current back-end already has rooms, member life cycles and security restrictions, but there is no mutually agreed friend relationship, temporary idle state that can invite users, user shielding and isolation, or ordinary room invitations. After completing these capabilities, users can find people to communicate with without introducing private messages and group chats, and the room host can safely invite each other into the room.

## What Changes

- New friend request and two-way friend relationship: initiation, viewing, acceptance, rejection, withdrawal and deletion are all verified by the server. Unilateral requests will not directly establish a friend relationship.
- Added user-to-user targeted blocking: blocking will atomically unfriend the two parties, terminate pending friend requests and unfinished invitations; unblocking will not automatically restore historical relationships.
- Added idle state based on short-term heartbeat and room membership/presence. Idle means the user has been online recently and is not currently in any room; the precise online duration, location or room activity details are not disclosed.
- Add a new friend list and inviteable user list, use stable cursor paging, and perform shielding and isolation and account, age, and security restriction filtering in both directions.
- Added room host to send room invitations to friends or currently inviteable users, as well as a closed loop for invited users to view, reject, and consume invitations through the existing join portal. Invitations do not reserve a quota, and cannot bypass password, capacity, age, account, security restrictions or room finality checks.
- Invite and friend write operations use a caller-generated UUID request identifier, enabling safe retries and preventing concurrent duplicate relationships or duplicate invitations.
- Extending NestJS code-first OpenAPI, PostgreSQL migrations, Redis presence, audit events and automated acceptance evidence.

Confirmation scope: The friend ability is only used for friend/idle status and room invitations. Private messages, group chats, followings, contact imports or recommendation algorithms are not provided. Users are blocked from isolating social lists, friend requests and ordinary room invitations in this change; whether to hide the public room lists of both parties is a subsequent independent product decision.

## Capabilities

### New Capabilities

- `friend-relationships`: Mutually agreed friend requests, friend lists, relationship dissolution, concurrency and idempotent boundaries.
- `user-blocking`: Targeted blocking, two-way social isolation, relationship cleanup and unblocking behavior.
- `user-availability`: Short-term online heartbeat, idle state calculation, minimum data projection and privacy filtering.
- `room-invitations`: room host ordinary invitation, invitation list, rejection/consumption, expiration and reuse of existing room qualifications.

### Modified Capabilities

None.

## Impact

- `apps/api/prisma/`: Added enumerations, models, constraints, indexes and migrations for friend requests, friend relationships, user blocking and room invitations.
- `apps/api/src/modules/social/`: Added social domain, application, HTTP DTO/controller, Prisma repository and Redis presence adapter.
- `apps/api/src/modules/rooms/`: Consume ordinary invitations and reuse room qualifications, passwords, and capacity rules in an existing join transaction; room host invitations continue to be verified through the rooms public application API.
- `apps/api/src/modules/audit/`: Records important status changes of blocking, friend relationships and room invitations, but does not record precise online time or redundant information.
- `openapi/openapi.yaml`: New entry and stable error response generated by NestJS code-first.
- No new external provider is added; PostgreSQL remains the source of truth for relationships and invitations, and Redis only saves temporary presence with TTL.
