## Why

The identity and data backend has provided trusted `userId` and `PROFILE_REQUIRED`, `AGE_RESTRICTED`, `ELIGIBLE` admission results, but the product still does not have a room API for front-end integration verification. The next step is to implement the server control plane for instant room discovery and joining, so that the list, creation and joining pages in the design can be developed around the real OpenAPI contract, while the capacity, password and access rules are fixed on the backend.

## What Changes

- Implement the back-end closed loop of `instant-room-discovery` confirmed requirements: Qualified users can create instant rooms of 2–6 people, with a default duration of 2 hours, and support public rooms and 4-digit password rooms.
- Provides authenticated instant room list, details, creation and joining API; list and details return topic, CEFR, current number of people/cap, start/end time, room host nickname and password status.
- Use room host as the first valid member after creation; repeated additions maintain idempotent and do not repeatedly occupy capacity.
- Perform account status, information/age, room status, rule confirmation, password and capacity verification in the join transaction; at most one request can succeed when competing for the last quota concurrently.
- Use server-side pepper's HMAC to save and verify the 4-digit room password, without saving or returning the plaintext password.
- PostgreSQL additive migration to add room and membership relationships, repository/application/domain layering, stable error code, NestJS code-first OpenAPI output and corresponding units, integration and HTTP E2E evidence.

### Confirmed Scope

- Only implements `openspec/specs/instant-room-discovery/spec.md` and the `localization-and-room-rules` confirmation boundary that the server needs to execute when checking in, and does not modify these current requirements.
- The room capacity includes room host; when the creation is successful, the current number of people is 1.
- The password status can be disclosed, but the password content cannot be disclosed; password comparison must use constant time comparison.
- PostgreSQL saves room and member facts and guarantees capacity through transaction/row locks; Redis double-write is not currently introduced separately for this one.
- OpenAPI continues to be deterministically generated by NestJS code-first, and `openapi/openapi.yaml` remains the only release contract.
- `implement-identity-profile-backend` is not archived yet; this change relies only on its implemented and verified identity, session, and admission application APIs.

### Non-goals

- Does not implement LiveKit token, audio publish/subscribe, real-time presence, disconnection reconnection or webhook.
- Room host transfer, member removal, re-invitation, active termination, room extension or safety officer operations are not implemented.
- Room reservation, friends, idle personnel, room history, reporting, STT, AI or post-meeting vocabulary are not implemented.
- Does not implement front-end page, Figma restore, generated frontend client or unified product acceptance.
- Do not establish the 3/12/24-hour temporary limit and appeal model that have not been defined by the current requirements; currently only verify that the account is available and the data/age access results are verified.

### Future Roadmap

- Next backend change access LiveKit voice credentials, room host control, leave/handover, 60 seconds reconnect and room end.
- Basic reporting, auditing and temporary restrictions are implemented in independent security changes.
- Redis is only introduced where presence, cross-instance coordination, or capacity caching has proven a need, PostgreSQL continues to be the source of truth for members.

### Unresolved Decisions

- There are currently no product decisions blocking this change. The departure of ordinary members of the room, the departure of the room host and the number of people online in real time belong to subsequent LiveKit/host-controls changes and do not define new behaviors in this batch.

## Impact

- Impacted delivery stages: Architecture、Backend / API、Test / Acceptance。
- Mainly affects `apps/api/src/modules/rooms`, the public application boundary of profiles/auth, `apps/api/prisma`, API testing, and `openapi/openapi.yaml`.
- Add room password pepper configuration; do not introduce Redis, LiveKit or new service processes.
- Add real-time room and membership tables and indexes to the database; migration must be able to forward upgrade from the existing identity/profile schema, rollback uses application rollback and forward fix, and no destructive down migration of existing data is performed.
- After the change is completed, only the back-end/API integration verification conditions will be provided. Product acceptance will continue to be postponed according to user requirements until the front-end is completed.
