## Context

The room operation details are currently generated by NestJS code-first DTO to generate a unique OpenAPI contract, and the query only accepts cursors and limits. The front-end room page already has a 1440×900 V2 main frame, and the Figma Desktop Bridge confirms the four filter controls of `114:1602`. See `proposal.md` and capability specifications for details.

## Goals / Non-Goals

**Goals:** Backend staff can perform server-side combination filtering and stable paging for all rooms, and see the real results corresponding to the current conditions on the page.

**Non-Goals:** does not add room disposal permissions, friendly short numbers, filtering by number of members or export of production reports. "Full" is still a display label calculated based on the current number of people and capacity, and the filtering status uses the actual room status.

## Decisions

1. Add optional `q/status/visibility/from` to the existing `GET /v1/backoffice/operations/rooms`. `q` removes leading and trailing blanks; the complete UUID accurately matches the ID, otherwise a case-insensitive inclusion query is performed on the subject. Length, status and value fields are checked at the DTO layer. Continue to use NestJS code-first to generate OpenAPI and do not maintain the second contract.
2. The server sorts creation time and ID in reverse order; the cursor contains filter fingerprints and verifies that the conditions are the same. Compatible with old unfiltered cursors, new filtered cursors cannot be used across conditions. The query is still limited to the page size and selects only operational fields; the query operation is retained for audit and the original search terms are not recorded.
3. The admin app uses a form to submit search terms, select status/visibility/7 or 30-day range; reset page number when conditions change. The lower time bound is fixed to the ISO time when selecting to avoid cursor failure caused by recalculation during page turning. Responsive and empty reuse of existing room card layout.

## Risks / Trade-offs

- [Subject inclusion queries may slow down on large tables] → Limit the search length and page size, first verify with the existing index and test scale; after going online, the real query plan will determine whether to add a trigram index.
- [Design draft short number without contract field] → The page clearly displays the real UUID abbreviation; the complete UUID is searchable, and the short number does not pretend to be a searchable field.
- [The server time boundary is different from the browser clock] → The lower bound of 7/30 days is fixed by the browser when the user selects it; the actual query is executed according to this ISO time and the cursor fingerprint is written.

## Migration Plan

No data migration. Publish compatible optional query parameters and OpenAPI first, and then publish the management terminal using the new parameters. After rolling back the admin app, the old unfiltered request continues to work; the server can be rolled back independently, and the old paging response remains unchanged. Acceptance includes contract generation, combination filtering and cursor regression, 1440×900 visual comparison, true native API queries; no device-specific behavior.
