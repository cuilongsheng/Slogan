## Context

房间运营明细当前由 NestJS code-first DTO 生成唯一 OpenAPI 合同，查询只接受游标和 limit。前端房间页已有 1440×900 V2 主框架，Figma Desktop Bridge 确认 `114:1602` 的四个筛选控件。详见 `proposal.md` 和能力规格。

## Goals / Non-Goals

**Goals:** 后台人员能对全量房间做服务端组合筛选、稳定分页，并在页面看到当前条件对应的真实结果。

**Non-Goals:** 不新增房间处置权限、友好短编号、按成员数筛选或生产报表导出。“已满”仍是由当前人数与容量计算的展示标签，筛选状态使用实际房间状态。

## Decisions

1. 在现有 `GET /v1/backoffice/operations/rooms` 追加可选 `q/status/visibility/from`。`q` 去除首尾空白；完整 UUID 精确命中 ID，否则对主题做大小写不敏感的包含查询。长度、状态和值域在 DTO 层校验。继续使用 NestJS code-first 生成 OpenAPI，不维护第二份合同。
2. 服务端以创建时间和 ID 倒序；游标包含筛选指纹并验证条件相同。兼容旧的无筛选游标，新增筛选后的游标不能跨条件使用。查询仍限定页大小且仅选择运营字段；审计保留查询操作，不记录原始搜索词。
3. 管理端用表单提交搜索词、选择状态/可见性/7 或 30 天范围；条件变化重置页码。时间下界在选择时固定为 ISO 时间，以免翻页期间重新计算造成游标失效。响应和空态复用现有房间卡片布局。

## Risks / Trade-offs

- [主题包含查询在大表上可能变慢] → 限制搜索长度和页大小，先以现有索引和测试规模验证；上线后由真实查询计划决定是否新增 trigram 索引。
- [设计稿短编号无合同字段] → 页面明确展示真实 UUID 缩写；完整 UUID 可检索，短编号不冒充可检索字段。
- [服务端时间边界与浏览器时钟不同] → 7/30 天下界由浏览器在用户选择时固定；实际查询按该 ISO 时刻执行并写入游标指纹。

## Migration Plan

无数据迁移。先发布兼容的可选查询参数与 OpenAPI，再发布使用新参数的管理端。回滚管理端后，旧无筛选请求继续工作；服务端可独立回滚，旧分页响应不变。验收包括合同生成、组合筛选和游标回归、1440×900 视觉对照、真实本机 API 查询；无设备专属行为。
