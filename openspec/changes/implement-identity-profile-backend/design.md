## Context

See Why of [proposal.md](./proposal.md). This design implements the existing [identity-and-profile spec](../../specs/identity-and-profile/spec.md) without modifying product requirements.

Currently `apps/api` only has the ESM startup shell of NestJS + Express and the Zod environment configuration verification; there is no database, public API, authentication, OpenAPI contract or business module implementation yet. This change spans auth, users, profiles, database, OAuth and HTTP bootstrap, and introduces persistence and public interfaces for the first time, so it is processed as Level 2.

## Goals / Non-Goals

**Goals:**

- Create trusted `userId`, session and user admission results that can be reused by subsequent rooms, voice, moderation.
- Ensure that third-party login idempotent, refresh token can be revoked and rotate safely, and admission qualifications will be recalculated immediately after the date of birth is modified.
- Generate a unique, machine-verifiable OpenAPI contract and align implementation, testing, and subsequent generated clients.
- Decouple domain policy from OAuth, Prisma, and NestJS transport, but only create the abstractions you really need.

**Non-Goals:**

- Does not build generic IAM, RBAC, microservices, event bus, or second database abstraction.
- OAuth provider access/refresh token is not saved; currently only the one-time authorization result is consumed to establish platform identity.
- Does not process public personal information, account merging, mobile phone number registration, administrator interest configuration or room permission implementation.
- Do not use automated fake provider results to replace Google/WeChat real environment acceptance.

## Decisions

### 1. Using NestJS code-first generated OpenAPI

`openapi/openapi.yaml` generated by a deterministic script using NestJS controller/DTO, `@nestjs/swagger` and validation metadata as implementation input. The repository only publishes this YAML as the only API contract; it is not allowed to maintain another handwritten OpenAPI.

CI/local check will regenerate the contract and compare it with the submitted file to avoid that the controller has changed but the contract is not updated. The first batch of interfaces use the `/v1` prefix, and the error adopts a stable structure: `code`, `message`, optional `details` and `requestId`, and the package success response is not unified.

The alternative API-first can freeze the protocol earlier, but it is currently a single-person NestJS greenfield project, and handwritten schema and DTO mapping will increase repeated maintenance. If API-first is required in the future, it must be switched through an independent Architecture change, and two sets of sources cannot be maintained in parallel.

### 2. The authentication process uses provider authorization code exchange

The mobile terminal obtains a one-time authorization code from Google or WeChat and calls `POST /v1/auth/oauth/{provider}/exchange`. The backend provider adapter uses the allowed redirect URI and the parameters required by PKCE/provider to complete the exchange and identity verification, only accepts `issuer + subject` after provider verification, and does not use email as the unique account key.

`OAuthProviderPort` only exposes the currently required `exchangeAndVerify()`; Google and WeChat implement adapters respectively. The test environment uses deterministic fake through dependency injection. When the non-test environment lacks provider configuration, the corresponding interface returns `AUTH_PROVIDER_UNAVAILABLE` and must not be automatically downgraded to fake login.

Provider token is not persisted. The provider nickname or avatar can only be used as a suggested value for the first data form and cannot bypass user submission and server-side data verification.

The alternative "client directly submits provider user information" cannot prove identity; the complete Passport strategy adds implicit control flow when there are currently only two exchange entries, so it is not used.

### 3. Platform session uses short-term access JWT + rotating opaque refresh token

- access JWT defaults to 15 minutes, including `sub=userId`, `sid=sessionId`, `iat`, `exp` and issuer/audience; the server guard verifies the signature, issuer and audience at the same time.
- The refresh token is a random value of at least 256 bits, and the default is 30 days; the API only returns plain text once, and the database saves the HMAC-SHA-256 digest with server pepper.
- Each refresh replaces digest within the transaction and updates the rotation time. The reappearance of the used token is considered a replay, the session will be revoked and `REFRESH_TOKEN_REUSED` will be returned.
- `POST /v1/auth/logout` Cancel the current session; users can have multiple independent device sessions, and there is no upper limit for the number of devices in this batch.
- access/refresh TTL, issuer, audience, and pepper are provided by the Zod-validated environment configuration; the above values ​​are security defaults and are not product requirements.

The token pair is returned via JSON, suitable for Expo secure storage; the management cookie session is outside the scope of this change. In addition to verifying JWT, subsequent room interfaces must also check user access and penalty status in real time, and cannot only trust the old status in the access token.

The alternative long-term JWT cannot be revoked in time; saving clear text refresh tokens on the server will expand the impact of leaks; a single global session will accidentally damage multiple devices, so it is not used.

### 4. PostgreSQL is the identity source of truth, Prisma only exists in infrastructure

The first schema uses UUID primary keys and UTC time, and contains at least:

- `User`: Platform account, account status, creation/update time.
- `OAuthIdentity`: `provider`, `issuer`, `subject`, `userId`, and establish a unique constraint on `(issuer, subject)`.
- `AuthSession`: `userId`, refresh digest, expiration/rotation/revocation time and minimum device description.
- `UserProfile`: avatar, name, gender code, nationality code or city, interest code list, CEFR, birth year/month, completion time.

The first OAuth login searches or creates identity and user in a database transaction; the unique constraint is responsible for resisting concurrent repeated logins, and the adapter rereads the unique-conflict as the same account. Prisma model is not exposed to application/domain beyond the repository adapter.

This batch does not create a dynamic interest directory table. `interestCodes` is saved as a code array with an upper limit on quantity, length and format; the administrator-configurable directory belongs to the subsequent capability, which will be normalized through migration, and details in the frozen PRD that have not yet entered the current spec will not be implemented in advance.

The alternative of putting the OAuth identity field directly into `User` would block future multi-provider bindings; the pre-built configuration center for all profile options is over-design and therefore not used.

### 5. The profiles module has data integrity and adult access policies

`profiles` domain defines data value objects, integrity rules and `RoomEligibilityPolicy`; `auth` is only responsible for identity and session, and `users` is only responsible for the platform account life cycle. Subsequent rooms query the access results through the application API exposed by profiles and do not read the profile repository.

The birth information only has year and month. In order to avoid allowing users who are actually under 18 years old to enter the room in advance when their birthday is unknown, the access time is defined as "00:00 UTC on the 1st of the next month after the end of the 18th birthday month". This will be delayed by less than a month at most, but is within the conservative security boundaries of a public voice room. The age is recalculated every time the data is submitted and the age is not permanently cached in the JWT.

Data status returned:

- `PROFILE_REQUIRED`: Any required field is missing or invalid;
- `AGE_RESTRICTED`: The data is complete but the conservative age of adulthood has not yet been reached;
- `ELIGIBLE`: The information is complete and the person has reached adulthood.

The first batch of endpoints are:

- `POST /v1/auth/oauth/{provider}/exchange`
- `POST /v1/auth/refresh`
- `POST /v1/auth/logout`
- `GET /v1/me`
- `PUT /v1/me/profile`

`PUT /v1/me/profile` accepts the complete profile representation and maintains idempotent, which is used for first initialization and allows the user to correct the data; changes in birth year and month will immediately recalculate the status. Currently there is no endpoint for querying other people's information by user ID.

### 6. The first batch of public APIs simultaneously establish minimum security and observability baselines

HTTP bootstrap access to Helmet, configured CORS allowlist, global validation pipe, exception filter, request ID, Pino/pino-http and authentication entrance flow limit. Logs provider type, internal user/session ID, result code and time consumption, but does not record authorization code, token, mobile phone number or complete profile content. Use Pino directly without adding the `nestjs-pino` packaging layer to avoid compatibility issues between its CommonJS build and NestJS 12/Jest ESM runner.

Current limiting uses in-process storage first because there is currently no cross-instance deployment or Redis consumer; it only protects a single instance. When entering multi-instance deployment or room Redis change, change to Redis-backed storage and supplement concurrent verification.

### 7. Acceptance evidence and requirement traceability

Each HTTP e2e scenario references the corresponding Requirement/Scenario of `identity-and-profile` in the test name or test description. Required:

- domain unit test: data integrity, CEFR/field verification, year and month boundaries and three access statuses;
- repository integration test: first creation, concurrent idempotent, transaction rollback, session rotation and revocation;
- HTTP e2e: first login, second login, data incomplete, data completed, under 18 years old, refresh replay, unauthenticated access and provider failure;
- clean database migration, lint, typecheck, build, test and dependency boundary results;
- Regenerated `openapi/openapi.yaml` without drift;
- Authorization success/cancellation/invalid code runtime evidence obtained using real Google/WeChat test applications. Missing credentials must be marked BLOCKED and must not be marked PASS.

This change has no UI and no visual/device evidence is required. OpenSpec criteria, contract, runtime and test evidence together constitute acceptance; production deployment is not an archive prerequisite.

## Risks / Trade-offs

- [Risk] The native OAuth parameters and audit conditions of WeChat and Google are different, which may block the acceptance of real providers → Use independent adapters and stable internal identities to record environmental blocking respectively; do not let the implementation of one provider pollute the other.
- [Risk] Self-reported birth month cannot prove true age → Make it clear that this is a lightweight boundary and use a conservative month algorithm; document or third-party age verification is left to subsequent requirement changes.
- [Risk] In-process current limit is not shared between multiple instances → Currently only single instance operation is accepted; the Redis-backed limiter must be migrated before multiple instances.
- [Risk] code-first decorator, validation and generator versions may cause contract drift → Fixed direct dependency versions, build script sorting output, and compare build results in CI.
- [Risk] Stolen refresh token may allow session takeover → High entropy tokens, digest-only, rotation, replay revocation, log masking and secure storage reduce risk.
- [Risk] `interestCodes` needs to be migrated to the administrator directory in the future → keep the fields bounded and encapsulated through profile repository, and use additive migration and compatible read migration later.
- [Trade-off] The conservative adult algorithm will delay some users who are over 18 years old in the current month to the next month → Current security takes precedence over an admission delay of up to one month; if accurate birthdays are required, the requirements and collection fields must be modified first.

## Migration Plan

1. Add dependencies, environment schema and sample configuration, without changing the default listening behavior of the existing startup entry.
2. Add Prisma schema, generate first additive migration, perform upgrade on empty PostgreSQL and verify repeat execution strategy.
3. Implement modules, adapters, HTTP security baseline and endpoints; test first using fake OAuth adapter and independent test database.
4. Generate `openapi/openapi.yaml`, perform contract drift, lint, typecheck, build, unit, integration, e2e and dependency boundary checks.
5. Configure the Google/WeChat test application and then add real provider runtime evidence; the project owner completes the acceptance review.

When rolling back, roll back the application version first to make the new interface unreachable. For development environments that have not entered production and have no retained data, the dedicated development database can be deleted and migrated again; destructive down migration will not be performed after real account data exists, and the newly added tables will be retained and restored through forward fix. The OAuth provider can be individually disabled by configuration, but the fake provider cannot be enabled.

## Open Questions

- When will the client ID/secret, redirect URI and test account of each environment of Google and WeChat be provided by the project owner? This only affects real provider evidence and does not change the module design or automation tasks.
- Do the access token 15 minutes and refresh token 30 days need to be adjusted after the first round of real device integration verification? Both have been configured, and the adjustment will not change the contract.
