## Context

See proposal.md for the observed request fan-out. ChatScreen currently calls detail (every15s), messages and callHistory (every3s); DirectApi hardcodes50. The repository's message cursor means sequence greater than last sequence, oldest-first; call history advances by mutable stateSequence. DirectConversation.nextSequence already orders text creation, call creation and call state revisions. Chat currently has no older-edge pagination handler. Root unread refresh is driven by the broad messages invalidation and explicit read completion.

The released outbox supports only rooms/partners/messages. The global stream carries public discovery topics and per-owner Redis streams carry private changes. PostgreSQL triggers and managed recovery already provide cross-instance publication. The stream and root provider currently reject social-ineligible actors, so simply subscribing restriction/report screens would not work. Existing recovery IDs are actor-bound and bounded. Keep that ownership and actual API/Pages streaming adapter.

## Goals / Non-Goals

Goals: complete current mobile product-change coverage through the existing connection, correct long-chat entry/paging, precise invalidation and demonstrable idle request reduction. See the specs for external behavior.

Non-goals: a second chat stream, sending business contents in invalidations, replacing media, notification to backgrounded phones, redesigning UI or moving product-list polling inside an SSE function. A bounded server reconciler for external release metadata is distinct from per-client polling of owned database projections.

## Decisions

### 1. Extend the existing envelope and scope authorization

Use the current /v1/me/live-updates endpoint and root LiveUpdatesProvider. The released parser throws on unknown scope values, so new event kinds MUST NOT be sent to an old connection. Add an optional generated query parameter protocol with default1 and supported value2. New clients request protocol2 on their one root connection; this is version negotiation on the same endpoint, not a second stream. Default/v1 connections retain the exact scope-only legacy frame vocabulary and existing eligibility policy. Protocol2 carries typed kinds and optional opaque resource references and supports topic-specific self-service authorization. The server skips unsupported entries while advancing internal replay positions safely; periodic renewal/reset remains bounded. A healthy protocol2 lease continuation emits ready with a fresh recovery ID, without broadcasting reset and causing unchanged snapshot reads; genuine gaps and new sessions still reset. Bind new recovery cursors to actor and protocol, and keep existing v1 cursor decoding valid. Reject cross-protocol recovery cursors or reset them under an explicit documented compatibility rule rather than mixing audiences.

In the new parser, safely ignore valid future kinds without terminating the connection and advance recovery IDs. Scope-only legacy private messages notifications remain in the outbox for old inbox/unread consumers during coexistence. The protocol2 adapter maps each committed event to its precise new topic and avoids emitting both the legacy broad message invalidation and its duplicate typed invalidation to the same new consumer. New chat consumers subscribe only to resource-specific conversation-history/state events. Add a coexistence HTTP test using the actual released parser: version1 never receives a scope it rejects while version2 receives the intended typed event. Existing production smoke currently speaks version1; extend it explicitly to version2 before claiming the new event path has cloud acceptance.

Keep authentication/session revocation at the existing auth boundary. For protocol2, replace the blanket social eligibility gate with topic authorization: valid non-trial authenticated users can receive their permitted own-account/report/appeal changes, while social/room/private peer topics remain independently qualified. Disabled/revoked sessions still close; public trial viewers remain excluded. Authorization is rechecked before private deliveries and at the existing bounded lease. Never trust resource IDs as permission grants. Store fan-out recipients by owner at commit time and re-evaluate access on delivery where a topic has changing role/membership requirements. Membership removal sends a minimal own-membership invalidation to the removed actor; no subsequent room content or host-only reference is allowed.

### 3. Add one merged timeline query without changing legacy cursor meaning

Add GET /v1/conversations/{conversationId}/timeline through the direct module's existing layers and NestJS code-first DTO generator. It supports mutually exclusive modes: no cursor (latest20), before (older20) and after (revision changes20). Return a discriminated text/call union, visibleAfterSequence, nextBeforeCursor/hasOlder, syncCursor, nextAfterCursor/hasMoreChanges. Server defaults and caps this endpoint at20; legacy message/call endpoints retain their forward50-compatible semantics.

Initial and older pages order by stable creation sequence, merging the latest at most20 entries from bounded indexed text/call queries, and serialize them chronologically. Opaque history cursors bind actor, conversation, direction, earliest position and the initial creation high-water mark. This means a new message cannot shift an older page boundary. Call status updates do not move a call's creation position. Recheck the current personal hiddenThrough boundary on every query.

Incremental reads use DirectMessage.sequence and DirectCall.stateSequence as change revisions. Capture rows and the conversation revision high-water mark in a consistent read transaction so a write between snapshot and watermark cannot be skipped. Sort delta candidates by change revision, merge by stable entry identity, and advance only through the returned bounded batch. If no more rows exist, advance to the captured high-water mark; do not reuse a non-null cursor as evidence of another page. A change to an old call updates that call in place and does not restart history scanning. Hidden/read visibility metadata is returned even for an empty delta. Add indexes where actual query plans require them, with an upgrade test and representative EXPLAIN evidence.

The unified20 budget includes text and call timeline entries because the current UI mixes them. No separate50-message plus50-call initial request pair remains. Server mutations still use ordinary authorized commands and idempotent caller request IDs.

### 4. Separate paging, synchronization, display and read acknowledgements

Create a feature-owned chat timeline state model with an older-history cursor, independent sync watermark, stable identity map, pending send state and account/conversation/focus generation fences. Use the root resource subscription; establish it before the initial snapshot and queue events arriving during initial/older loads. Coalesce bursts while retaining a pending refresh so invalidations during requests cannot disappear. Continue bounded after pages only when hasMoreChanges says so; do not auto-walk before pages.

Render the existing virtualized timeline, preserving its compact Figma bubbles/composer. On initial entry, position at latest after layout. At the older edge, prepend one page and preserve the visible anchor; use platform-verified list anchoring/inversion rather than assuming browser pixel offsets are native evidence. Incoming content scrolls only when already at the latest end. Older call updates do not insert a new bubble. Do not load all history into memory at entry; virtualization remains enabled. No arbitrary loaded-history truncation silently discards the reader's anchor.

Use separate metadata/history and unread responsibilities. A read command advances only the highest actually viewed incoming text sequence while focused/foreground/near the latest end, never a call revision or unseen latest text while reading history. Coalesce read completion and its matching SSE invalidation into one unread reconciliation. Newer changes arriving during that reconciliation queue one follow-up rather than disappearing. Own command responses merge immediately; matching echoed events deduplicate by identity/revision. Failed commands preserve drafts/idempotency IDs. Account replacement clears pending actions and blocks late send/read/page mutations.

## Risks / Trade-offs

- Expanded topic authorization can leak private or moderation state → minimal resource references, explicit audience matrix, current-host/revoked-member/third-account negative tests and no business payloads.
- Unknown new scopes disconnect the released SSE parser → default-to-v1 protocol negotiation, exact legacy frames and an actual old-parser coexistence test before new clients ship.
- Reusing old forward cursors for backward history would break released clients → additive endpoint and direction-bound cursors, coexistence test before client cutover.
- Snapshot/delta/older-page races can skip content or resurrect hidden history → consistent watermark snapshot, stable creation bounds, current hiddenThrough checks and lifecycle generations.
- Read invalidations can create self-sustaining request loops → separate history/unread event kinds, one coalescing scheduler and explicit idle/read-loop request-count assertions.
- Removing room fallback before publisher completeness can delay removal/end → verify all admin/worker/webhook/timeout paths and cloud negative media-callback tests before removing15s polling.
- Extra per-member outbox rows and expanded topics cost resources → transition-only publication, bounded batches, reuse Redis readers, measure fan-out/backlog and avoid load/billing claims from smoke samples.
- External release metadata lacks transactional push → one managed reconciler with distributed lease plus foreground/manual authoritative checks; no per-client server polling or invented immediate-delivery SLA.
- Native prepend/keyboard/background behavior differs from web → target-device evidence separate from browser fixture results.

## Migration Plan

1. Approve the Level2 design and scope inventory; reconcile older changes that explicitly retain chat/call/invitation polling. Keep this proposal pending until reviewed; do not silently rewrite current requirements.
2. Ship the additive event/schema/timeline backend with compatibility handling, code-first OpenAPI and complete transactional publishers. Test upgrade over existing data, no-op filters, permission isolation, consistent paging and old-client behavior.
3. Verify incremental API/Pages delivery and all new audience boundaries with owned fixtures, actual reset/abort/renewal, resource/backlog receipts and cleanup. Test external release reconciliation against fixed fixture metadata.
4. Migrate each consumer in the inventory, including the non-eligible self-service path, and verify zero periodic change-detection queries. Preserve outbound leases and media/device callbacks.
5. Run final affected checks, original/runtime comparison and current device acceptance; record explicitly accepted limitations. Use the separately authorized guarded backend-first/client-second release process and record actual commits/artifacts if deployment is requested for this follow-up.
6. Roll back the client to the previous compatible release if needed, retaining all business records, legacy endpoints and additive event schema; forward-repair publishers without destructive data deletion. Do not perform a production rollback merely to manufacture evidence.
