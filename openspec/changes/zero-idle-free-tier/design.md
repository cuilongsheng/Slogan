## Context

Managed queues pin messages to a deployment. A lease prevents overlap but cannot prevent obsolete deployments taking turns. Existing recurring full authorization/recovery scans dominate idle cost.

## Goals / Non-Goals

Implement the four phases requested on 2026-10-18. Preserve all permission, replay, provider command and expiry invariants. Do not alter mobile transport or introduce services. Free-tier fit for continuous SSE is not promised.

## Decisions

1. One durable `ManagedWorkerOwner` per database, with deployment ID and monotonically increasing generation. Activation is an explicit release operation with compare-and-swap expected generation, never first-request auto-election. Business producers read this row and pin messages to the owner. Workers reject unstamped/wrong-deployment messages before bootstrap where possible, then compare the durable fence before work. Each continuation rechecks the fence. Existing work may finish; stale work cannot publish. Existing room command leases/idempotency remain. A global owner intentionally spans Preview/Production when they share a database.
2. No realtime recovery chain. One owner-fenced maintenance fallback every 900 seconds online/pending, or 3600 seconds confirmed empty, probes bounded existence hints; only relevant work enters domain recovery/transactions. Retain the existing APK release metadata check in this same fallback (SET NX + GET and a small HTTP read, at most once per 15 minutes active or once per hour empty), publishing only on a changed version. This explicitly justified residual prevents silently removing release SSE notifications. Its SET NX/GET adds 1,440 Redis commands/month when confirmed empty (<=5,760 while continuously online); the repair EVAL also has internal commands and is counted separately in quota planning; optional metadata fetch failure does not fail unrelated cleanup. Actual business mutations wake publication immediately and queue needed work. Presence has explicit expiring generation jobs; no global 15-second sweep in SSE/heartbeat. Local development retains its existing workers.
3. Full token signature validation on request entry; reuse a server-created verified context. A single narrow authorization-state SQL read includes session validity, preview/trial scope, adulthood and effective restriction booleans; never returns passwords, email or full profiles. Periodic SSE checks remain at most 15 seconds and additionally precede retained event delivery. No cross-request authorization cache. Align 15-second checkpoints and bounded 240-second renewal deadlines across subscribers, so staggered subscriptions do not multiply idle reads. Early renewal at the next shared boundary remains protocol-compatible. Suppress optional Redis CLIENT SETINFO metadata, retain readiness checks.
4. Snapshot query projections remove unused profile fields. The shared reader retains at most 200 buffered valid events per temporarily authorizing subscriber, rejecting overflow for cursor-based reconnect instead of dropping events. Established stream keys remain readable during authorization, preventing unnecessary cancellation on every subscriber checkpoint. Cold reconciliation does not trust a missing process cache and obtains a narrow active-member snapshot once. Historical membership needed for stale-token/removal authorization cannot be indiscriminately discarded; reconciliation must request active plus explicitly relevant target members.
5. Metrics source versions count append-only revision rows, one per committed source-mutating transaction, inserted by source-table triggers. This avoids a shared counter row and lock-order deadlocks. Aborted transactions are invisible. Revision storage grows with real mutations and is not purged independently of the watermark. A completed window/version/source-version tuple skips aggregation. Capture version before computation so a concurrent mutation always makes the completed result eligible for another computation. Monitoring defaults to 900 seconds and remains disabled by default, especially in Preview.
6. PostgreSQL pool retains max=10 (the prior pg default) with explicit idle timeout=60s and allowExitOnIdle=true. Testing max=2 exposed existing host transactions that acquire another pool connection for profile eligibility while holding a room lock; reducing the cap can starve that transaction. Keep this change scoped rather than rewriting the room transaction boundary; no keepalive timer or function extension.

## Risks / Trade-offs

A durable fence costs one narrow DB read on accepted managed deliveries and producer sends. The user approved a 60-minute fallback when confirmed empty (no indexed presence, rooms or pending work), retaining 15 minutes online/pending. Shared Lua cardinality avoids classifying a partially repaired presence index as empty. New business hints and the first live expiry delivery restore the shorter cadence once; common quarter-hour idempotency keys merge both chains at shared boundaries. Exceptional lost first scheduling from empty state may wait up to an hour. The fallback is for missed scheduling only; normal deadlines are scheduled from durable work. On Hobby with a shared Preview/Production database, activate the current fenced Production deployment as the global owner so its canonical daily cron can reseed it; Preview business producers route to that owner. A Preview-only owner needs explicit release reseeding and is not accepted as an unattended cron-backed rollout. One global owner requires routing credentials to work across the project deployment environments; hosted acceptance must prove this. A safety scan cannot claim zero queries, CPU, or bandwidth. Existing unfenced consumers must be retired; this code cannot control old binaries. Continuous 2 GB SSE still consumes allocated memory during I/O wait.

## Migration Plan

Apply additive migrations, deploy a fenced candidate without activating it, verify queue routing/protocol compatibility, activate with expected generation and deployment ID, seed the fallback once, then retire all legacy unfenced consumers. No migration or release is executed here. Restore work from durable PostgreSQL/Redis on activation. Never promote an unfenced rollback binary.

## Rollback

Activate a compatible fenced deployment with a NEW higher generation. Do not decrement generation. Keep additive schema/triggers through rollback; remove triggers only after dependent code is retired. Preserve durable outbox/commands and their existing deduplication keys. If queue routing cannot be proved, do not activate.

## Verification

Each phase runs build/typecheck/lint and focused unit/integration/e2e. Final verification covers revoke, restrictions, member removal, reconnect, replay, presence expiry, outbox, pending commands, stale owner and metrics late data. Resource budgets are source-derived with instrumented command/query counts where practical; no unmeasured cloud CPU claim.

## Redis accounting

Budget conservatively includes EVAL and every Lua-internal command, matching official Upstash rate-limit cost examples, not only network/SDK sends. Local Redis MONITOR with synchronization barriers verifies that distinction. Steady presence uses SET EX GET instead of EXISTS plus SET, preserving atomicity and reducing actual internal work. Hosted quota deltas and global replication remain release evidence, not local claims.
