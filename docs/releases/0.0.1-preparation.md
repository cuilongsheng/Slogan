# 0.0.1 release preparation

Status: `planned` (2026-10-02). No production environment or release artifact has been selected or deployed.

## Decisions recorded for this release

- Product owner has excluded email, WeChat, SMS, and post-room keywords from the first release. The corresponding OpenSpec capability deltas still need to record the release boundary; existing historical changes are not silently rewritten here.
- Username/password login is intended for real users, without email. Current registration/reset requires email and SMTP, so a separate authentication change and its migration, abuse controls, and account recovery acceptance are required before this is release-ready.
- Backoffice should have one platform administrator and one distinct safety officer. The current local database has one user holding both roles; the second account and audited role change remain to be performed after the no-email login path exists.
- The initial deployment platform and domain have not been chosen. `docs/runbooks/deployment.md` therefore has no target-specific rollout commands yet.

## Artifacts and checks already available

- API: NestJS build, Prisma migrations, generated `openapi/openapi.yaml`, PostgreSQL and Redis development/test Compose files, backup/restore scripts, and startup configuration checks. `pnpm --filter @slogan/api build` passed on 2026-10-02. These are local capabilities, not production verification.
- Admin: Vite static build and Playwright test infrastructure. `pnpm --filter @slogan/admin build` passed on 2026-10-02.
- Mobile: Expo project, `pnpm --filter @slogan/mobile typecheck` passed, and an Android debug APK built locally on 2026-10-02. No physical Android device was connected for installation or two-device voice acceptance.
- Realtime: LiveKit Cloud integration has local browser evidence. Public webhook reachability and two physical devices still require the deployed environment.

## Deployment work in dependency order

1. Approve the first-release OpenSpec scope and complete no-email username/password signup, login, recovery, frontend flows, and migration verification. Keep email/WeChat/SMS/keyword features disabled in the release configuration.
2. Choose a hosting region/platform and domain. Confirm HTTPS ingress for API, admin, OAuth redirects, room links, and LiveKit webhooks; decide where PostgreSQL and Redis run and how encrypted backups are retained.
3. Create reproducible production API/worker and admin artifacts, isolated production configuration, CI gates, secret injection, database migration command, health probes, and rollback artifacts. Do not put `.env` files or provider keys in images or the repository.
4. Provision two distinct user accounts. Use the audited backoffice role API to grant `SAFETY_OFFICER` to the second account and revoke it from the bootstrap administrator, leaving exactly one active `PLATFORM_ADMIN` and one active `SAFETY_OFFICER` on separate users.
5. Select an AI expression provider whose data-use terms satisfy the configured no-training and retention policy; smoke-test a private text-only expression request, quota failure, and provider outage. Free trial credit alone is not production availability evidence.
6. Run migrations and smoke checks in staging with real DNS/TLS, Google OAuth, LiveKit webhook, two accounts/devices, admin permissions, backup/restore, and failure rollback. Record evidence and environment identifiers without secrets.
7. Only after staging acceptance, prepare the production release record with included archived changes, image digests, configuration changes, migration result, smoke results, rollback point, and `deployed` status.

## Current blockers

No deployment target/domain; no approved no-email authentication and recovery flow; no two-device Android runtime evidence; no verified production AI provider policy; no distinct safety-officer account. This record is preparation, not a production release claim.
