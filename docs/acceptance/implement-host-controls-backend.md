## Implemented server behavior

- [HostControlsService](../../apps/api/src/modules/rooms/application/services/host-controls.service.ts) verifies the current room host, account, member lifecycle, target room and credentialVersion in the Room row lock; successfully commits mutation, RoomEvent, and RealtimeCommand with the same transaction. Expected rejection action saves DENIED audit, and stores exceptions as a whole rollback.
- ACTIVE takes up capacity; LEFT/REMOVED/INVITED does not take up capacity. LEFT or INVITED When re-entering successfully, update the original membership, assign a new identity, increment the credentialVersion, and use the historical maximum joinOrder plus one. If the network is disconnected abnormally, it remains ACTIVE. The current member presses joinOrder to display continuous positions.
- leave/remove/invite request carries expectedCredentialVersion. Repeated actions for the same submitted generation are not successfully audited; old requests encounter the new generation after reentry and return ROOM_OPERATION_CONFLICT. Removal cannot be directed at yourself or other room members; ordinary members cannot designate a successor.
- Before re-inviting, verify the invitee's account, onboarding, open status and capacity, and do not reserve a seat. The actual join re-verifies the account, rules, password, capacity and window; the deactivated account cannot be restored through re-invitation or direct application join.
- Room host leave only selects successors who are ACTIVE, online, and have valid accounts. Reject if invalid and not replace by default; select the smallest joinOrder if not specified. Atomic update of role and hostUserId, original room host LEFT; if there is no candidate, the public end entry is called.
- Room host active end, no successor, disconnection timeout, no candidate reuse OPEN → ENDING → ENDED. ENDING means rejecting join/token, and ENDED occurs only after the actual revocation and DeleteRoom are completed. Expiration end takes precedence over timeout handover.
- Room host disconnection saves 60 seconds deadline, independent hostReconnectVersion, audit and HOST_TIMEOUT outbox in the original presence transaction. The clearing window will be restored in time; settlement will be triggered after the deadline, and late events cannot regain the transferred room host permissions. Use the trusted observation time of reconciliation when the real provider Webhook is lost, and do not backtrack to the unknown disconnection time.
- When the window is not settled, ACTIVE can repeatedly join and restore credentials; new users, LEFT, and INVITED joins return ROOM_HOST_RECONNECTING and details.retryAt, and the unsettled window cannot be bypassed even if the deadline has passed.
- The original RealtimeRunner schedules the persistent HOST_TIMEOUT as a host-timeout job in the same BullMQ queue, starts/recovers every 15 seconds; the database command contains the original identity and reconnect version, rechecks the deadline when executing, and no-ops duplicate or invalid tasks. Ordinary member actions only change the general stateVersion and do not invalidate valid window tasks.
- Continue to use the original provider dispatcher/try again. REVOKE_IDENTITY only waits for the valid issuance lease of the target identity to prevent other members from refreshing credentials and dragging the removal; DELETE_ROOM is still waiting for all valid issuances and revocations to be completed. The revocation of the old identity will not be applied to the new identity generated after the re-invitation.

## Only HTTP Contract

[NestJS controller](../../apps/api/src/modules/rooms/presentation/host-controls.controller.ts) and [DTO](../../apps/api/src/modules/rooms/presentation/dto/host-controls.dto.ts) generate [openapi/openapi.yaml](../../openapi/openapi.yaml). All four new entrances require user Bearer:

| Endpoint                                                   | Input and output                                                                                                       |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| POST /v1/rooms/{roomId}/leave                              | expectedCredentialVersion; room host can bring successorMembershipId; return exit/takeover/end status                  |
| POST /v1/rooms/{roomId}/members/{membershipId}/removals    | target expectedCredentialVersion; current room host only                                                               |
| POST /v1/rooms/{roomId}/members/{membershipId}/invitations | Removed target expectedCredentialVersion; invitation does not occupy space                                             |
| POST /v1/rooms/{roomId}/end                                | The current room host actively terminates; repeated calls return the current result or stabilize permission conflicts. |

The existing join/detail projection adds lifecycle, credentialVersion and hostReconnectDeadline; members only returns ACTIVE, continuous position and minimum public fields; realtime-credentials returns the current lifecycle/role/generation/window, which is still the minimum audio permission limited to the room.

Management response contains roomStatus with providerStatus=COMPLETED/PENDING/UNAVAILABLE. 200/PENDING indicates that the database action has been submitted and cleanup is still queued; the details of 503/REALTIME_PROVIDER_UNAVAILABLE saves the results of the submitted action and cannot be interpreted as transaction rollback. Deletion after undo recovery may be completed in the next schedule, during which ENDING remains. FAILED commands that reach the pre-retry limit need to be operated and restored according to the pre-acceptance record, and the identity history cannot be deleted or the room reopened to bypass authorization.

Stable error override ROOM_HOST_REQUIRED, ROOM_MEMBER_NOT_ACTIVE, ROOM_INVITATION_REQUIRED, ROOM_SUCCESSOR_INVALID, ROOM_HOST_RECONNECTING, ROOM_OPERATION_CONFLICT, ROOM_ACCOUNT_RESTRICTED, and existing capacity, qualification, end, provider errors.

## Data migration and rollback boundaries

[20260912040000_host_controls](../../apps/api/prisma/migrations/20260912040000_host_controls/migration.sql) is an independent additive migration; new lifecycle, leave/remove fields, host reconnect fields and HOST_TIMEOUT enum are added. The original row defaults to ACTIVE. There is no repeated creation of realtime tables or rewriting of already implemented migrations.

[Migration test](../../apps/api/test/integration/host-controls-migration.spec.ts) Verify empty database upgrade chain and existing LiveKit data upgrade in independent random schema of real PostgreSQL: retain connection status, membership/joinOrder/generation/identity, ENDING room, pending command and events; check enum, foreign keys and ACTIVE query index. Transaction rollback walkthrough confirms that REMOVED limit and pending command are not lost.

Release should be migrated first, and then new authorizations and workers should be deployed in the same batch. Old certification programs that do not understand lifecycle cannot be mixed. Before rolling back, join/token/management must be closed at the portal, and the provider session cancellation and termination must be completed; when the provider is unavailable, keep the portal closed and retain workers, waiting for recovery or forward fix. The database retains the newly added fields and history, and does not perform destructive down migration. The above release rollback steps of ingress isolation and Cloud cleanup are operational requirements and have not been practiced in a real deployment environment; local transaction rollback testing cannot replace it.
